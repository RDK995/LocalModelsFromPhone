# Build one free search service, layer the fallbacks

*Research date: 2026-09-29. All version, status and pricing facts are as of that date unless stated.*

The best no-payment alternative to SearXNG for this Mac Studio is **not one product but a small local search service inside (or beside) the existing Bun server**: use the **`ddgs` Python library** (MIT, v9.16.0, 26 Aug 2026) as the keyless primary, because it queries ten engines (DuckDuckGo, Bing, Brave, Google, Mojeek, Startpage, Yahoo, Yandex, Wikipedia and more), needs no Docker, and ships its own tiny HTTP API and MCP server; back it with **card-free hosted quotas** (Tavily 1,000/month, Exa $10/month of credit, You.com 100/day, Ollama's own web_search on a free account) that only get used when scraping fails; and read pages with **Defuddle on linkedom inside Bun**, which ran in about 15 ms in a hands-on test on this machine. The Bun-native metasearch engine **degoog** is the strongest self-hosted alternative if you want a SearXNG-shaped server, but it ships with zero search engines installed and its engine health is unverified. Every free option that works by scraping is in an arms race: in 2025–26 Whoogle stopped returning results and was archived, Mullvad Leta shut down, and even SearXNG lost its classic Google engine and fought DuckDuckGo CAPTCHAs. So the durable design choice is a **single local HTTP endpoint with pluggable backends and a cache**, which the phone server calls directly and OpenCode reaches through a custom tool or a small MCP wrapper. OpenCode's built-in `websearch` is unsuitable: it sends queries to Exa or Parallel (chosen at random per session) and is hidden for Ollama providers anyway, while its `webfetch` is already local and free. Brave's API, the old go-to free tier, now requires a credit card and meters overage, which rules it out.

## Scraping works from a home IP, but only with several engines and a cache

The core problem every free, keyless option shares is that it reads public search result pages that the engines do not want read by machines. The 2025–26 record is blunt. **Google has required JavaScript for search since about 17 January 2025**, which killed simple scrapers such as `googlesearch-python` ([Michael Tsai](https://mjtsai.com/blog/2025/01/24/google-search-now-requires-javascript/)). Whoogle's README now says it "no longer returns search results, and that isn't something this project can fix", and the repo was **archived on 2026-08-14** ([Whoogle](https://github.com/benbusby/whoogle-search)). Mullvad **shut down Leta in November 2025**, citing anti-bot measures and CAPTCHAs ([TechRadar](https://www.techradar.com/vpn/vpn-services/mullvad-says-goodbye-to-proxy-search-citing-big-changes-in-the-search-industry)). SearXNG itself disabled its classic `google` engine after it had "been not working for almost a month" in July 2026 ([searxng #6453](https://github.com/searxng/searxng/issues/6453)), and in late August 2026 every DuckDuckGo query on self-hosted instances hit a challenge page until SearXNG switched to browser-TLS impersonation via curl_cffi ([searxng #6596](https://github.com/searxng/searxng/issues/6596)). Even after the fix, a maintainer puts DDG reliability at **"around 90%"** ([searxng #6779](https://github.com/searxng/searxng/issues/6779)).

The encouraging reading of those same threads is that most failures were **fingerprint-based and fixed by code updates**, not volume-based. One user's agent making tens to low hundreds of queries a day from a residential IP is the easiest case a scraper can face. That makes two design rules non-negotiable: query several engines so one blocked engine does not mean no results, and keep the library current. It also argues for a local cache and a rate limit in the Bun server, since an LLM can fire a burst of near-identical queries that trips per-IP limits; SearXNG, for instance, suspends an engine for **24 hours after a CAPTCHA and 7 days after a Google reCAPTCHA** by default ([SearXNG docs](https://docs.searxng.org/admin/settings/settings_search.html)). All of this scraping is against the engines' terms of service; the practical consequence for a home user is soft IP blocks rather than legal exposure, and `ddgs` itself says it is "for educational purposes only" ([ddgs](https://github.com/deedy5/ddgs)).

## Ranked options: ddgs first, degoog second, hosted quotas as insurance

The table ranks every option that survives the "no payment, no card" rule for this specific setup (macOS, no Docker, Python 3.14 and Bun, low volume, shared with OpenCode later).

| Rank | Option | What it is | Cost / card | Install on this Mac | Main risk |
|---|---|---|---|---|---|
| 1 | **ddgs** | Python multi-engine scraper library with optional HTTP API (port 4479) and MCP server | Free, no account | `pip install "ddgs[api]"` in a venv | Silent "no results" when an engine blocks; 3.14 native deps unverified |
| 2 | **degoog** | Bun/TypeScript metasearch server, SearXNG-compatible JSON, MCP sidecar | Free, AGPL-3.0 | `bun install && bun run build && bun run start` | Ships zero engines; extension quality unverified |
| 3 | **Card-free hosted APIs** (Tavily, Exa, You.com, Ollama web_search, SerpApi, LangSearch, Linkup) | Real APIs with monthly free allowances | Free account, no card | An API key per provider | Quotas change; queries leave the machine |
| 4 | **4get** | PHP metasearch actively re-patching its Google scraper | Free, AGPL-3.0 | PHP plus curl-impersonate | Heavier native setup; API shape unverified |
| 5 | **Marginalia, Wiby, Mwmbl, Wikipedia** | Independent indexes | Free (Marginalia personal key by email) | Plain HTTP | Coverage far too small for general search |
| 6 | **Playwright-driven Google** (e.g. web-agent-master/google-search) | Real headless browser | Free | Chromium download | 1–3 s per query, CAPTCHAs, highest upkeep |

### ddgs gives multi-engine search without running a search engine

**`ddgs`** (formerly `duckduckgo-search`) is the lowest-effort route to what SearXNG provides. Its `text()` search can use **bing, brave, duckduckgo, google, grokipedia, mojeek, startpage, yandex, yahoo and wikipedia**, with `backend="auto"` to spread across them, proxy support, and a 5-second default timeout; `pip install "ddgs[api]"` adds a FastAPI server and `ddgs[mcp]` adds a stdio MCP server ([PyPI ddgs](https://pypi.org/project/ddgs/)). The API server listens on **port 4479** and also offers content extraction ([ddgs](https://github.com/deedy5/ddgs)). The Bun server can call `http://127.0.0.1:4479` or spawn the CLI; either way it is one small process under a LaunchAgent. The weaknesses are documented in its own tracker: a DuckDuckGo 403 (#480, July 2026), rate-limit errors that are never raised as a catchable exception (#478), and a bug where one failing backend drops results from successful ones (#427) ([ddgs issues](https://github.com/deedy5/ddgs/issues)). Open WebUI users reported DDG-via-ddgs "No results found" in May 2026 ([open-webui #24428](https://github.com/open-webui/open-webui/issues/24428)). The realistic failure is therefore an empty list, not an error, so the Bun side must treat "zero results" as a failure and fall through to the next backend. It requires Python 3.10 or later; nobody has confirmed its native dependencies on 3.14 specifically, so this is the first thing to test. There is no comparable JavaScript library: `duck-duck-scrape` is DuckDuckGo-only and Snyk flags it as possibly discontinued ([Snyk](https://snyk.io/advisor/npm-package/duck-duck-scrape)).

### degoog is the SearXNG replacement that speaks Bun

If you want a proper self-hosted search server rather than a library, **degoog** fits this stack best. It is TypeScript on **Bun**, describes itself as "a more modular lighter alternative" to SearXNG, had commits on the research date, and released **0.26.0 on 2026-09-13** ([degoog](https://github.com/degoog-org/degoog)). Its `/api/search` returns JSON (title, URL, snippet, source, score), streams per-engine results over SSE, and can emit **SearXNG-shaped responses with `format=json`**, so anything built for SearXNG's API can point at it ([degoog API docs](https://degoog-org.github.io/docs/api.html)). It also ships an MCP sidecar example aimed at LLM clients. The catch is deliberate: degoog "ships with zero search engines installed", and engines come from a vetted extension store, with pluggable fetch "transports" such as curl or FlareSolverr ([degoog docs](https://degoog-org.github.io/docs)). Its SearXNG compatibility layer runs SearXNG engine modules through a Python bridge, which would pull Python back in. Nobody in this research confirmed which working Google, DuckDuckGo or Brave extensions exist today, so degoog's real-world result quality is the biggest open question.

### Hosted free tiers are good insurance, not a foundation

Several AI-oriented search companies still offer recurring, **no-card** allowances, and the structural advantage of no card is that the worst case is a refusal, never a bill. **Tavily** gives **1,000 credits a month** and stops requests at the cap ([Tavily pricing](https://www.tavily.com/pricing)). **Exa** credits **$10 at signup and resets to $10 on the first of each month** ("up to 2,500 Instant searches"), no payment method required ([Exa pricing](https://exa.ai/pricing)). **Ollama's `web_search`/`web_fetch`**, launched 2025-09-24, needs only a free Ollama account and is built for exactly this tool-calling use, but its "generous free tier" has **no published number** and its pricing page does not mention search at all ([Ollama blog](https://ollama.com/blog/web-search); [Ollama pricing](https://ollama.com/pricing)). **You.com** added **100 free calls a day** on 2026-07-29, reported only by a pricing-diff tracker so far ([UsagePricing](https://www.usagepricing.com/blueprint/activity/you-com-2026-07-29-web-search-free-tier)). **Linkup** tops accounts back to **$20 a month** (about 4,000 standard searches) but only for sign-ups with a "professional email address", which likely excludes a Gmail account ([Linkup docs](https://docs.linkup.so/pages/documentation/platform/pricing)). **LangSearch** is nominally free with daily token caps, but its published limits conflict and it describes itself as free "as we build AGI together" ([LangSearch limits](https://docs.langsearch.com/limits/api-limits)). SerpApi (250/month) and Serper (2,500 one-time) come from secondary sources only.

Ruled out on cost or availability: **Brave Search API** ended its free 2,000-query plan on **2026-02-12** and now requires a card that meters overage ([Implicator.ai](https://www.implicator.ai/brave-drops-free-search-api-tier-puts-all-developers-on-metered-billing/); [Brave](https://brave.com/search/api/)); **Google Custom Search JSON API** is closed to new customers and ends **2027-01-01** ([DEV Community](https://dev.to/nexgendata/google-kills-custom-search-api-on-jan-1-2027-you-have-9-months-1jg1)); **Bing Web Search API** was retired **2025-08-11** ([Microsoft Learn](https://learn.microsoft.com/en-us/lifecycle/announcements/bing-search-api-retirement)); Perplexity Sonar needs a payment method; Mojeek's API is paid from £2 per 1,000 queries with only an unquantified trial ([Mojeek](https://www.mojeek.com/services/search/web-search-api/)). Privacy differs too: Tavily's policy lets it use query data to improve its service and share queries with third-party index providers ([Tavily privacy](https://www.tavily.com/privacy)), while Ollama publishes no retention statement for search at all.

### Everything else is either too small, too heavy or dead

The independent indexes are honest and free but narrow. **Marginalia** has a documented JSON API with a free non-commercial key by email (a shared "public" key often returns 503), but it deliberately indexes the "small web" ([Marginalia API](https://about.marginalia-search.com/article/api/)). **Wiby** has a keyless JSON endpoint for classic-web pages ([Wiby](https://wiby.me/json/)). **Mwmbl** is alive, but its own evaluation shows **4.8% recall** for its index alone, and its new combined endpoint is capped at **100 requests a month** ([mwmbl PR #439](https://github.com/mwmbl/mwmbl/pull/439)). These are useful as extra sources, not a primary search. Among self-hosted metasearch engines, **4get** is actively maintained and its author was re-patching Google scraping on 2026-09-08, but it needs PHP with curl-impersonate ([4get](https://git.lolcat.ca/lolcat/4get)); **LibreY** (PHP) and **websurfx** (Rust plus Redis) are alive but weaker fits; **YaCy** is a Java peer-to-peer crawler suited to indexing known sites, not general search. **Vane** (formerly Perplexica) is not an alternative at all: it consumes SearXNG ([Vane](https://github.com/ItzCrazyKns/Vane)). **LibreX**, **Stract**, **Whoogle**, **Farside** and **Leta** are dead or archived. Playwright-based Google tools can beat the JavaScript wall, some with a pop-up browser window for a human to solve CAPTCHAs ([web-agent-master/google-search](https://github.com/web-agent-master/google-search)), which rules them out for unattended phone use.

The steelman for staying with SearXNG deserves stating. It remains the most active project in this space (issues opened daily, curl_cffi impersonation already landed), installs natively on Python 3.14 now that msgspec 0.20 fixed the known 3.14 blocker ([searxng #5284](https://github.com/searxng/searxng/issues/5284)), and its JSON format is the de facto interface that Vane, Open WebUI and degoog all speak. If you build against SearXNG's JSON shape, you can swap SearXNG, degoog or a ddgs adapter behind it later without touching either client.

## Page reading stays local, fast and free

Turning a URL into clean text is the easier half, and it needs no third party. The in-process JavaScript stack works under Bun with no native modules: in a hands-on test on this Mac (Bun 1.4.0), **Defuddle 0.19.4 on linkedom** returned markdown in about **15 ms**, stripped navigation and footer, and kept a fenced code block's language tag; **Readability plus Turndown** ran in about 11 ms but lost the code language; **trafilatura 2.2.0** installed cleanly on Python 3.14 and ran in about 4 ms but **flattened a code block into inline code and invented a date** from a copyright footer. All three passed an injected "Ignore previous instructions." line straight through, so extraction is not a prompt-injection defence. On published benchmarks, trafilatura scores **0.924 F1** in its maintainer's 990-document evaluation ([trafilatura](https://github.com/adbar/trafilatura/blob/master/docs/evaluation.rst)), while a smaller 2026 vendor test gives Readability a 0.94 median F1 versus trafilatura's 0.91, noting that Readability drops content on docs pages with many equal sections ([BulkMD](https://bulkmd.app/blog/readability-vs-trafilatura-extractors)). No independent benchmark includes Defuddle, whose README still says it is "very much a work in progress", so pin its version ([Defuddle](https://github.com/kepano/defuddle)).

The recommended pipeline is Defuddle first, then plain whole-page Turndown if the extract is suspiciously short, and a headless browser only when the page body is nearly empty (a JavaScript app). **Crawl4AI** (Apache-2.0, pip-installable, downloads its own Chromium) is the no-Docker option for that last step ([Crawl4AI](https://docs.crawl4ai.com/core/installation/)); Firecrawl and Jina Reader's open-source build are documented only as Docker deployments. The hosted **r.jina.ai** reader works **with no key at 20 requests per minute** and says it never trains on requests ([Jina Reader](https://jina.ai/reader/)), but it sends every URL the model reads to a third party. A free bonus: sites on paid Cloudflare plans now return server-side markdown to clients that send `Accept: text/markdown`, cutting Cloudflare's own blog post from **16,180 to 3,150 tokens** ([Cloudflare](https://developers.cloudflare.com/changelog/post/2026-02-12-markdown-for-agents/)), so the fetcher should send that header.

The real risk in page reading is not quality but **server-side request forgery**: a model, or a page it reads, can ask the fetcher to open `127.0.0.1`, a LAN device, or a tailnet address and read back an admin page. The fetcher must resolve DNS itself, reject any private address in every A and AAAA answer, follow redirects manually and re-check each hop, and allow only http and https ([OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)). For this setup the blocklist must include **`100.64.0.0/10`, which covers every Tailscale node and the `100.100.100.100` service address** ([Tailscale](https://tailscale.com/kb/1015/100.x-addresses)). Whether Bun's `fetch` supports pinning a resolved IP is unverified, so test with `localtest.me`, a redirect to `127.0.0.1` and `http://2130706433/`. Cap body size (OpenCode uses 5 MB), time and output tokens, and label fetched text as untrusted.

## OpenCode can share the same backend through one custom tool

OpenCode's built-in `websearch` is a thin client for **two hosted services, Exa (`mcp.exa.ai`) and Parallel (`search.parallel.ai`)**. In the pinned 1.18.21 binary it is hidden for any provider other than OpenCode's own unless `OPENCODE_ENABLE_EXA`, `OPENCODE_ENABLE_PARALLEL` or the broad `OPENCODE_EXPERIMENTAL` is set, and when neither backend is forced it **picks one by hashing the session ID**, so queries go to one of two companies unpredictably; Parallel also receives the session ID and model name with each query. Users reported the switching ([opencode #39121](https://github.com/anomalyco/opencode/issues/39121)), and a PR to let local providers opt in cleanly was closed unmerged on 2026-09-23 ([opencode #44343](https://github.com/anomalyco/opencode/pull/44343)). Exa's keyless tier is reportedly **3 queries per second and 150 calls a day**, from a secondary source ([Scalekit](https://www.scalekit.com/blog/exa-mcp-vs-api)). OpenCode cannot be pointed at a self-hosted backend through configuration, but it offers three supported replacement routes: an MCP server entry, a custom tool file in `.opencode/tools/`, or a plugin. **A custom tool with the same name as a built-in takes precedence** ([OpenCode custom tools](https://opencode.ai/docs/custom-tools/)), and MCP tools are prefixed with the server name so they can be allow-listed as `"search_*": true` ([OpenCode MCP](https://opencode.ai/docs/mcp-servers/)). OpenCode's `webfetch`, by contrast, is **entirely local** (a GET with a Chrome User-Agent, a 5 MB cap and Turndown conversion), so only search needs replacing ([OpenCode tools](https://opencode.ai/docs/tools/)).

That makes one shared backend straightforward. Run a single local search endpoint, ideally exposed by the Bun server itself as `GET /search?q=…` returning SearXNG-shaped JSON, that tries ddgs, then the hosted free tiers, caches results, and rate-limits. The phone chat path hands it to Ollama as ordinary `web_search` and `web_fetch` function tools; Ollama does not speak MCP, so there is no benefit to MCP on that side. OpenCode reaches the same endpoint through a roughly 20-line `.opencode/tools/websearch.ts` or through an existing MCP client such as **mcp-searxng** (MIT, about 1.3k stars), which only needs a SearXNG-compatible URL ([mcp-searxng](https://github.com/ihor-sokoliuk/mcp-searxng)); `ddgs[mcp]` and degoog's MCP sidecar are alternatives. Because the harness runs OpenCode inside a sandbox, this adds a new egress path (sandbox to the host search port) that the containment policy must allow explicitly, and the launcher should scrub the `OPENCODE_ENABLE_*` and `OPENCODE_EXPERIMENTAL` variables so the Exa/Parallel path never appears. One untested point: whether a custom tool named `websearch` escapes the 1.18.21 provider gate. The MCP route is not affected by that gate, so it is the safer default until a quick live test settles it.

## What remains uncertain

Several load-bearing facts are thin. No source gives measured per-engine success rates for a single home IP in 2026; the "about 90%" DuckDuckGo figure is one maintainer's anecdote. `ddgs` on Python 3.14 and degoog's current engine extensions are both untested, and those are the two things to check before committing. Ollama's free search quota, Exa's and Parallel's keyless limits, and You.com's new daily tier are unpublished or secondary-sourced, and free tiers across this market changed repeatedly in the past year. No independent benchmark compares result quality of ddgs, degoog, 4get or SearXNG against Google, and Defuddle's quality claims are its author's. Finally, all scraping options breach the scraped engines' terms, and any of them can break for days until a maintainer patches it.

## Conclusion

The 2025–26 history reframes the question. Asking "which product replaces SearXNG" treats search as a thing you install once, but the evidence shows every free backend, self-hosted or hosted, degrading or changing terms within months: Google's JavaScript wall, Brave's card requirement, Whoogle's archival and SearXNG's own engine suspensions all happened within about 18 months. The durable asset is therefore the interface you own, one local endpoint with a stable JSON shape, a cache, a rate limit and an ordered list of backends, not any single backend behind it. Built that way, ddgs today, degoog or SearXNG tomorrow, and a no-card hosted quota as the safety net become interchangeable parts.

This also changes what "free" should mean. Every card-free hosted tier here costs nothing but sends queries to a company whose free allowance and privacy terms can change without notice, while every self-hosted option costs nothing but maintenance time and a steady risk of breaking. Putting the self-hosted scraper first, hosted quotas second and a strict fetch-side safety fence around both keeps the phone app and the future OpenCode agent working on the same zero-cost footing, and ensures that when a backend breaks, one line of configuration changes rather than two clients.
