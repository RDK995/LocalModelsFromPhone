Goal:
Prove through the server's real HTTP entry point (POST /v1/chat with web enabled, as in server/src/http/webStop.test.ts and webReplyInProgress.test.ts) that:
(a) Both backends failed: when the search service answers POST /v1/search with 503 {"error":"search_unavailable"}, the reply's stream/event log contains a step with kind "search", status "unavailable"; the next request the fake Ollama receives contains a tool message telling the model search is unavailable; the fake Ollama then streams a final answer; the reply ends done with a normal (non-error, non-cancelled) status and the answer content.
(b) Time limit, search: when the search service holds POST /v1/search open past the web-tools client time limit (configure the client timeout small, e.g. 300-500 ms, via whatever option the server app already exposes for webTools timeoutMs — find it; add a test-only injection only if none exists), the step is status "failed" with detail "timeout", the model's next request contains a tool message saying the search failed, and the reply completes with the answer, within a bounded wall time (assert < 5 s).
(c) Time limit, page read: same as (b) for read_page / POST /v1/read: step kind "read" status "failed" detail "timeout", model told the page could not be read, reply completes.
(d) Search service's own time limit: POST /v1/search answered 504 {"error":"timeout"} -> step failed detail "timeout", model told, reply completes.
Each case ends with the generation no longer running (a following POST /v1/chat is admitted, not 409).
