TASK M20-T1 — Search helper tries each allowed ddgs engine on its own and reports why each one failed

Routing: tier Mid, model sonnet, reason_code ORDINARY_IMPLEMENTATION — ordinary change to one Python file and
its tests, but it changes the I17 output contract that M20-T2 depends on, and classifying real-world
rate-limit / CAPTCHA signals needs judgement beyond a mechanical edit.

Goal:
The helper (C14, search/helper/search.py) accepts an optional ordered list of allowed ddgs engines, tries
them one at a time, and reports a per-backend outcome for every backend it tried (each ddgs engine and the
browser), so the search service (C13) can rest a backend that was rate-limited or shown a CAPTCHA.

Relevant Requirements:
- FR39 (.harness/requirements.md lines 312-319), FR20 (lines 137-143). Region uk-en and no-account rules
  are unchanged.

Acceptance Criteria (this task provides the helper half of M20-AC1; verbatim):
- M20-AC1: "Search service tests through its HTTP search API with faked backends and a controlled clock: a
  backend returning rate-limit / too-many-requests is skipped for 1 hour and one returning a CAPTCHA or
  bot-check for 24 hours, searches go to the remaining backends then the headless browser meanwhile, and
  with every backend resting or failing the search is "unavailable" as in FR20."

Required behaviour (the contract M20-T2 builds on — implement exactly):
1. New optional CLI argument `--backends <comma-separated engine names>` (e.g. `bing,brave,duckduckgo`).
   - Absent: behave as today (one `client.text(..., backend` not passed / "auto") call) — existing tests
     must keep passing unchanged.
   - Present and non-empty: for each engine in order, call
     `client.text(query, region=REGION, safesearch="moderate", max_results=max_results, backend=<engine>)`;
     stop at the first engine returning at least one usable result.
   - Why one engine per call: ddgs 9.16.0's `text()` with several engines runs them in a thread pool and
     swallows each engine's exception (ddgs/ddgs.py ~line 200, `logger.info("Error in engine ...")`), so a
     rate-limited engine cannot be told apart. One engine per call makes each failure attributable.
   - Time: with `--backends` present, construct the client with a per-engine timeout of 4 s
     (`DDGS(timeout=4)`; keep `ddgs_factory` injectable — pass the timeout through or accept it via the
     factory) so four failing engines plus the browser stay inside the search service's 25 s limit.
   - Present and empty (`--backends ""`): no ddgs call at all; go straight to the browser step.
   - New optional flag `--no-browser`: skip the browser step (it is resting); treat as browser not tried.
2. Classify each attempt's outcome as exactly one of:
   `ok` | `empty` | `rate_limited` | `captcha` | `error`.
   - `rate_limited`: `ddgs.exceptions.RatelimitException`, or an exception whose text contains `429`,
     `too many requests` or `ratelimit` / `rate limit` (case-insensitive).
   - `captcha`: an exception whose text contains `captcha`, `bot check`, `unusual traffic`, `are you a robot`
     or `anomaly` (case-insensitive). For the browser step, a Bing page that is a challenge page (detect by
     page title/body text containing one of those markers, or a known challenge selector) is `captcha`.
   - Classification must be a small pure function with its own unit tests.
3. Output JSON gains an `attempts` list on BOTH success and error outputs:
   `{"backend": "<engine name or 'browser'>", "outcome": "<one of the five>"}` in the order tried.
   Success output stays `{"results": [...], "backend": "<engine name, or 'ddgs' when --backends absent, or
   'browser'>", "attempts": [...]}`. Error output stays `{"error": "search_failed", "detail": ..., "attempts":
   [...]}`. Existing keys and their meanings are unchanged; `attempts` is additive.
4. Existing test-only hooks (SEARCH_HELPER_FORCE_DDGS / SEARCH_HELPER_FORCE_BROWSER) keep working. Add
   `SEARCH_HELPER_FORCE_DDGS=ratelimit` and `=captcha` (every ddgs engine attempt behaves as that outcome)
   and `SEARCH_HELPER_FORCE_BROWSER=captcha`, documented in the module docstring, so later live checks can
   force them without the network.
5. Exit 0 always, one JSON object on stdout — unchanged.
