TASK M19d-F1 — A failed search does not end a sub-question's searching (review cycle 1, IMPORTANT finding; M19d-AC1, FR44 early end vs FR35 search floor)

Routing: tier Mid, model sonnet, reason_code ORDINARY_IMPLEMENTATION — a bounded correction to two

Problem (from .harness/reviews/M19d-cycle1.md, read it in full):
`webTools.search` returns `results: []` when a search FAILS (FR24 timeout, 5xx, network error,
503 search_unavailable) — see server/src/web/tools.ts `webSearch` failure branch (~lines 158-168),
which emits a `step` event with `kind: "search"` and `status: "failed"` or `"unavailable"`.
`searchOnce` in server/src/generations/research.ts (~lines 753-774) counts `added` without checking
whether the search succeeded, so a failed search returns 0 and:
- the round-1 loop (~lines 901-914) does `if (added === null || added === 0) { sq.searchOver = true; break; }`
- the later-rounds loop (~lines 943-953) does `if (added === 0) { sq.searchOver = true; continue; }`
One transient failure therefore ends the sub-question's searching; if it was the first search the
sub-question gets no page at all. Before M19d the loop moved on to the next query until the FR35
minSearches floor was reached.

Goal:
FR44's early end ("a search round adds no new URLs") applies only to a search that SUCCEEDED
(its search step status is not `failed`/`unavailable`) and added no new URLs. A failed search:
- still counts toward `sq.searches` / `maxSearches` (as now, so retries are bounded);
- does NOT set `sq.searchOver`;
- in round 1, the loop carries on to the sub-question's next query (up to its round-1 search count,
  i.e. the minSearches floor), then page choice and first note as usual;
- in later rounds, the sub-question is not ended by it; it may search again in a later round
  (subject to maxSearches, the gap check and the other existing end conditions).
A search that succeeds with zero results, or only already-known URLs, still ends searching exactly
as now (existing AC1b tests must keep passing unchanged).
Suggested shape: have `searchOnce` tell the caller the search failed (e.g. inspect the returned
`events` for a `step` event with `kind === "search"` and status `failed`/`unavailable`, and return a
distinct value or a small result object). Equivalent designs are fine. Do not change
server/src/web/tools.ts. Update any comment in research.ts that describes the early end so it says
"a successful search that adds no new URLs".
