TASK M18-T2 — The "Deep research" action beside Send, gated on the model the server reports

Routing: tier Mid, model sonnet, reason_code ORDINARY_IMPLEMENTATION — a pure view-model, one
per-send flag threaded through the existing send path, and composer wiring in chat.tsx; follows
the existing web-switch pattern.

Goal:
With a conversation's web switch on, the chat composer shows a "Deep research" action beside Send.
It is hidden with the web switch off; shown disabled with the line
"Load <model name> to use deep research" when another (or no) model is resident; enabled when the
resident model is the deep-research model the server reports in GET /v1/state
(`deep_research_model`, added by M18-T1 to `StateResponse` in shared/api.ts — the app hardcodes
no model name). Using it sends that one message as a deep research run (POST /v1/chat body has
`web: true` and `deep_research: true`); the next message sent with Send is an ordinary reply.

Relevant Requirements:
- FR34 (.harness/requirements.md lines 241-251); FR18 (web switch: no web traffic while off).
- Milestone criterion M18-AC2 (.harness/milestones.md, section "## M18").

Already done (M18-T1, read the code, do not change the server):
- shared/api.ts `StateResponse.deep_research_model: string`.
- The server refuses a deep_research request with web off (code `deep_research_needs_web`) or
  with a model other than the configured one (code `deep_research_model_not_loaded`, message
  "Load <name> to use deep research").

Acceptance Criteria:
- New pure module mobile/src/ui/deepResearch.ts exporting a view-model function, e.g.
  `deepResearchAction(webOn: boolean, state: { resident: ResidentModel | null;
  deep_research_model?: string } | null)` returning `{ visible: boolean; enabled: boolean;
  explanation: string | null }`:
  - webOn false -> visible false (whatever the model).
  - webOn true, resident name === deep_research_model -> visible, enabled, explanation null.
  - webOn true, other model or no model resident -> visible, disabled, explanation exactly
    `Load ${deep_research_model} to use deep research`.
  - webOn true but state unknown / no deep_research_model reported -> visible, disabled, with a
    plain explanation (e.g. "Can't tell which model deep research uses."); never a hardcoded name.
  `webOn` is the value the web switch displays (`webSwitchDisplayValue(...)` in ui/webSwitch.ts).
  Unit tests in mobile/src/ui/deepResearch.test.ts cover all branches, including one with a
  non-default model name (e.g. "some-other:7b") to prove nothing is hardcoded.
- mobile/src/chat/chatController.ts `SendMessageCallbacks` gains `deepResearch?: boolean`. When
  true, `sendMessage` (which already reads GET /v1/state before every send) sends
  `{ model: resident, messages, web: true, deep_research: true }` only if `callbacks.web === true`,
  the resident model has tools, and `resident === state.deep_research_model`; otherwise it makes no
  POST /v1/chat and calls `onBlocked` with the same explanation the view-model gives
  ("Load <deep_research_model> to use deep research"). When false/absent, behaviour is unchanged.
  Tests in chatController.test.ts with the existing fake-fetch pattern assert the exact request
  body in each case.
- mobile/src/chat/conversationSession.ts `sendInConversation` accepts the per-send flag through
  its existing `options` parameter (e.g. `options.deepResearch`), passes it to `sendMessage`, and
  does NOT persist it on the conversation. Tests in conversationSession.test.ts: a deep research
  send's request body carries `deep_research: true`, and a following send in the same conversation
  without the flag carries no `deep_research` key (an ordinary reply).
- The blocked path for deep research must not show the "No model loaded" / "Load a model" UI text
  for a model mismatch; it shows the deep-research explanation (adjust BLOCKED_MESSAGE handling in
  conversationSession only as needed so the message passed to `onBlocked` is the deep-research one
  in that case; existing blocked tests unchanged).
- A server refusal (409 `deep_research_model_not_loaded` / 400-or-409 `deep_research_needs_web`)
  surfaces as a plain sentence: add these codes to mobile/src/api/errorMessages.ts's mapping with
  tests (use the server's own message for the model one if the error carries it; otherwise
  "Load the deep research model to use deep research" / "Deep research needs web search to be
  on."). Check how mobile/src/api/client.ts turns a non-200 POST /v1/chat into an error first.
- mobile/src/app/chat.tsx: keep the latest GET /v1/state result's `resident` and
  `deep_research_model` (it is already fetched at ~line 143 for the web switch); render a
  "Deep research" button beside Send (same row, not while a reply is in progress — the Stop button
  replaces both), visible/enabled/explanation from `deepResearchAction`, explanation shown as a
  small line under the composer like the web-switch explanation. Pressing it sends the input text
  exactly like Send but with the deep research flag (refactor `handleSendMessage` to take an
  optional `{ deepResearch: boolean }` rather than duplicating it). The .tsx is not unit-testable;
  keep logic in the pure modules above.
