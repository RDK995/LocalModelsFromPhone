TASK M20-T2 — The search service rests a rate-limited backend for 1 hour and a CAPTCHA'd one for 24 hours

Routing: tier Mid, model sonnet, reason_code ORDINARY_IMPLEMENTATION — new module plus wiring in an existing
HTTP handler, fully settled by HTTP-level tests with a fake helper and an injected clock; shared state is
in a single-threaded Bun process, so no difficult concurrency.

Depends on: M20-T1 accepted (helper `--backends`, `--no-browser` and `attempts` output).

Goal:
In the search service (C13, `search/`), keep one circuit breaker per search backend (each allowed ddgs engine,
plus `browser`). A backend whose attempt came back `rate_limited` rests for 1 hour; `captcha` rests for 24
hours. Each POST /v1/search passes only non-resting engines to the helper (`--backends a,b`, `--backends ""`
if none) and `--no-browser` if the browser is resting. If every backend (all engines and the browser) is
resting, answer `503 {"error":"search_unavailable","detail":"all search backends are resting"}` without
spawning the helper. Every other existing response shape is unchanged.

Acceptance Criteria (verbatim):
- M20-AC1: "Search service tests through its HTTP search API with faked backends and a controlled clock: a
  backend returning rate-limit / too-many-requests is skipped for 1 hour and one returning a CAPTCHA or
  bot-check for 24 hours, searches go to the remaining backends then the headless browser meanwhile, and
  with every backend resting or failing the search is "unavailable" as in FR20."

Design decisions already taken (do not reopen):
- Breaker state lives in memory in the search service process (lost on restart; acceptable).
- Allowed engines, in order: from env `SEARCH_DDGS_BACKENDS` (comma-separated) if set, else the default
  `duckduckgo,bing,brave,mojeek`. Wire this in search/src/index.ts; the handler takes it via options.
- The clock is injected (`now: () => number`, ms) through the handler options; default `Date.now`.
- Resting boundaries: a backend that rested at time t is usable again at exactly t + 3_600_000 ms
  (rate-limit) or t + 86_400_000 ms (CAPTCHA). A later failure while resting cannot occur (it is not tried);
  a failure after reopening starts a fresh rest. `empty`, `error` and `ok` outcomes do not rest a backend.
- When the helper output has no `attempts` (older helper / timeout / abort), record nothing.
- The response body on success stays `{results, backend}`; do not add body fields.

Tests required (in search/src/http/ — a new test file, e.g. breakers.test.ts, using the existing pattern of
a fake helper command; see server.test.ts and src/search/search.test.ts for how a fake helper is wired):
1. Engine A returns `rate_limited` → next search's helper argv excludes A; at now+59 min still excluded; at
   now+60 min included again.
2. Same with `captcha` → excluded until +24 h, included at +24 h.
3. While A rests, the search is answered by the remaining engine or by the browser (assert the argv the fake
   helper received and the 200 response).
4. Browser CAPTCHA → `--no-browser` passed until +24 h.
5. All engines and browser resting → 503 `search_unavailable` and the fake helper is NOT spawned (assert
   spawn count); all trying-and-failing (helper error output) → 503 `search_unavailable` as today.
Fake helper: a tiny script (bun or sh) that records its argv to a file and prints scripted JSON, as existing
tests do; never run the real ddgs or a browser.
