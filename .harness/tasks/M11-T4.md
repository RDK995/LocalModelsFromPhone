Relevant Requirements:
.harness/requirements.md FR23 (lines 123-129), AC17 (246-248), AC18 (249-251). Criteria:
- M11-AC1: Killing the connection during a web reply and reconnecting yields the complete steps and
  answer with no gaps and no duplicates.
- M11-AC2: Persisted conversations contain each web reply's steps and sources but no page text or
  full search results, and a follow-up prompt sends prior answers with their source lists without
  re-sending page text.
- M11-AC3: While a reply is searching, sending another prompt is refused as a reply in progress, and
  a swap or unload requires the busy confirmation.

What the proof must do (assert each, print PASS/FAIL per check, exit non-zero on any FAIL):
1. Shell wrapper exactly in the shape of mobile/scripts/web-switch-proof.sh / resume-proof.sh:
   restart com.harness.server and com.harness.bundle-host LaunchAgents, wait for 401 on /v1/state
   (bounded for-loop as in those scripts; no while/until loops), record the resident model, run the
   .ts, and restore the resident model in a trap. Tee output to .harness/evidence/M11-T4-proof.log.
2. Start a web-enabled chat with a prompt that needs a search (e.g. a current-news question). As
   soon as the first `step` event arrives, while the reply is still searching:
   a. POST another chat -> refused 409 generation_in_flight (AC3).
   b. Request a model unload (and a swap if a second installed model exists) without confirm ->
      the busy-confirmation response including reply_in_progress; do not confirm (AC3).
3. Kill the connection (abort the stream) after at least one step event and before done; reconnect
   via the app client's resume path (or GET /v1/generations/{id}/events with Last-Event-ID). Collect
   to done. Then fetch a full replay from seq 0 of the same generation. Assert the dropped-prefix +
   resumed events equal the full replay by seq: contiguous, no duplicate, no gap; steps folded by
   step_id equal; content equal (AC1).
4. Drive the same kind of web reply through conversationSession with a store (as
   conversation-proof.ts does) and assert the persisted assistant message has non-empty `steps` and
   `sources` and only the allowed keys {id, role, content, thinking, model, status, generation_id,
   last_seq, steps, sources}; assert the serialized stored conversation contains no `tool` role
   messages (AC2 persistence).
5. Send a follow-up prompt in that conversation, capturing the outgoing request body (wrap fetch):
   assert the prior assistant message carries its "Sources:" block with every source URL, there are
   only user/assistant role messages, and the body contains no page text -- check that the body
   size is below content+sources length + prompt + a small margin (AC2 re-send).
6. Print the model used, generation ids, counts of events/steps/sources, and timings.
