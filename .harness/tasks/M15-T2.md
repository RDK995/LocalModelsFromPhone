Goal:
A deep research run module inside the generation manager (C6) — new file(s) under server/src/generations/ (e.g. research.ts plus research.test.ts) — that, given a user question, a chat client (the existing `OllamaChatClient` interface in server/src/generations/manager.ts) and web tools (C12), runs a fixed, server-owned sequence and yields events in the existing generation event shapes (step / source / content tokens / done), ending with a report. Not a model tool loop: no tools are offered to the model.

Sequence (FR35):
1. Brief — one model step restating the question as a short research brief.
2. Plan — one model step splitting it into sub-questions; the COUNT is a server setting (default 3), extra items dropped, missing ones tolerated.
3. For each sub-question: model step(s) proposing search queries; run at least the server-set minimum number of searches (default 2, max default 3) per sub-question with exact repeats after normalising (lowercase, trim, collapse whitespace) skipped; the model chooses pages to read ONLY by index among URLs the server parsed out of the search results (never a free URL); read them (existing read_page rules, via C12, default max 2 pages per sub-question); one note step per page producing short notes, each `{quote, claim}` where quote is meant to be verbatim from the page; the server attaches the page's number.
4. Gap check — a model step `{enough: boolean, next_query?: string}`; `enough` may end a sub-question early once the minimum searches are done, but a server cap on searches/reads always bounds it (the model is never the only stopping rule).
5. Write — one final model step producing the report from the notes only, citing pages as `[n]`.

Every model step: a narrow chat request whose reply is constrained by a JSON schema via Ollama `format` (the write step too, e.g. `{report: string}`), with the same explicit `options.num_ctx` (server setting, default 32768) on every request in the run, and `keep_alive: -1` (residency, FR4). The client from M15-T1 accepts `format`, `options`, `think`, `keep_alive` on OllamaChatRequest (server/src/ollama/client.ts) — use those fields; extend the `OllamaChatClient` interface only if needed. Parse only the answer content (`message.content` tokens), never the thinking. Validate the parsed JSON against the expected shape; on malformed/empty/invalid reply retry a bounded number of times (default 2 retries), then skip the step and continue the run (a skipped plan falls back to the brief/question as the single sub-question; a skipped write falls back to a non-empty FR33-style note — never an empty answer).

Context discipline: each request carries only stable instructions, the brief, the plan, the capped rolling notes (cap by total characters, server setting) and the latest result. Never a growing transcript; raw page text is used only in the note step for that page and then discarded. Page text is untrusted data: wrap it as data in the prompt; it can influence only notes and the choice among server-parsed URLs; nothing it says can cause any other action.

Citations by construction (FR37): each distinct page read gets a number in first-read order using the existing numbering (server/src/web/pageNumbers.ts createPageNumberer / pageUrlKey, as the ordinary web loop uses through webTools.execute's numberPage argument); source events as the ordinary web loop emits them. Each note's quote is checked by substring match after whitespace normalisation against that page's stored text (the read result text); non-matching notes are dropped before writing. Before the report is emitted as the final content, remove every `[n]` whose n is not a page read in this run, and remove any http(s) URL the model typed into the report.

Events: phases stream as `step` events. Add step kinds `"plan"` (covers brief+plan) and `"write"` to the StepEvent kind union in server/src/web/tools.ts; searches and reads reuse kinds `"search"` (with `query`) and `"read"` (with `url`) and their started/done/failed statuses exactly as C12 already emits them. The report is emitted as content after write finishes (one or more content tokens), then the run completes.

You may add a small structured helper to C12 (server/src/web/tools.ts) so the research loop gets search results as `{title,url,snippet}[]` and page text, if the existing `execute()` return is not enough — keep `execute()` and the ordinary loop's behaviour unchanged.

Settings (sub-question count, min/max searches, pages per sub-question, notes cap, num_ctx, retries) are constructor/options parameters with the defaults above, so tests can shrink them. Do not wire HTTP in this task (M15-T3 does); do not add deadlines, Stop handling beyond honouring the AbortSignal passed in, or resume (later milestones).
