TASK M16-T3 — An explicit `think: false` in a chat request reaches Ollama

Routing: tier=Cheap model=haiku reason_code=BOUNDED_LOW_RISK detail="small isolated change in one function's body construction with stated input/output; settled by unit tests against the existing fake Ollama"

Goal:
`OllamaClient.chat()` in server/src/ollama/client.ts currently builds the body with
`...(think ? { think: true } : {})` (~line 281), so a request carrying `think: false` sends no
`think` key and a thinking-capable model (e.g. qwen3.5) thinks anyway. Deep research steps send
`think: false` explicitly (M16-T2) and need it to reach Ollama.

Acceptance Criteria:
- When `request.think === false`, the /api/chat body contains `think: false` (even if /api/show reports the 'thinking' capability).
- When `request.think === true`, the body contains `think: true` (unchanged).
- When `request.think` is undefined, behaviour is exactly as today: `think: true` if /api/show reports 'thinking', otherwise no `think` key at all (existing tests at client.test.ts ~lines 172-260 and ~318 keep passing unmodified).
- New tests in server/src/ollama/client.test.ts written first (Red), in the existing "OllamaClient chat think capability" describe block style, covering: explicit false with a thinking-capable fake -> `think: false` sent; explicit false with a non-thinking fake -> `think: false` sent.
- Update the doc comment above `chat()` to state the explicit-false behaviour.
