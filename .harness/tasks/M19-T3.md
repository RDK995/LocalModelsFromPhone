TASK M19-T3 — The phone saves a deep research reply like any answer, keeps a stopped run's steps and sources, and resumes it after backgrounding

Routing: tier Cheap, model haiku, reason_code BOUNDED_LOW_RISK — app tests written from the stated
assertions below against existing session, store, history and resume code (M11/M18 already persist
research replies); a small code fix is in scope only where a stated assertion fails.

Goal:
App tests prove M19-AC3 for a deep research reply: it is saved with its report as the answer plus
steps, sources and status; page text and notes are not persisted; the next prompt carries the report
like any prior answer; a second-Stop reply (server ends it `done {status:"cancelled"}` with steps and
sources but no report content) reopens with its steps and sources and no report; backgrounding and
returning resumes the run without gaps or duplicates.

- Milestone criterion M19-AC3 (.harness/milestones.md, section "## M19").

Acceptance Criteria (each a test; write it first and run it; if it already passes against the
existing code, that is fine — keep it as the proof; if it fails, make the smallest fix in the allowed
files):
1. conversationSession.test.ts, new describe "sendInConversation: deep research saving and stop
   (M19)": a scripted deep research event stream (plan/search/read/write steps with elapsed_ms and
   budget_ms, a `sources` event, one report `content` event, done `complete` with
   `research:{status:"partial",...}`) is persisted as one assistant message whose `content` is the
   report, with `steps`, `sources` and `research` (status `partial`), and status `complete`. Assert
   the stored message has no page text and no notes: it has no keys other than the existing Message
   fields, and no stored string contains a page-text marker that the scripted read step/event
   carried only transiently (e.g. a step `detail`/excerpt if the stream carries one; otherwise assert
   on the exact set of keys).
2. Same describe: the next send in that conversation sends the report as the prior assistant turn's
   content (assert the exact request `messages` body sent to the fake client), and nothing else from
   the run (no steps, no sources text, no notes) unless the existing FR23 history rule for web
   replies already appends the source list — in that case assert exactly what that existing rule
   produces (read the M11 history tests in the same file first and follow them).
3. Same describe: a second-Stop stream (steps, `sources`, no `content`, done `{status:"cancelled"}`)
   is saved with status `stopped`, empty content, its steps and sources; reopened from a fresh
   ConversationStore over the same storage it has the same steps and sources and no report; and
   mobile/src/ui/chatItems.test.ts: building chat items for that reopened message shows the steps
   and "Sources (n)" and no answer text and does not throw.
4. mobile/src/api/resume.test.ts (or client.test.ts, whichever holds the existing M4c/M11 resume
   tests — follow that file's pattern): a deep research stream that drops after event id k and is
   resumed from the last seen id yields every step (with elapsed_ms) and the report exactly once, in
   order — no gaps, no duplicates — and ends with the `done` research status.
