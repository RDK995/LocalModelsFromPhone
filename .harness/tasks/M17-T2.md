TASK M17-T2 — The time budget as a server setting, and proof through POST /v1/chat

Routing: tier Mid, model sonnet, reason_code ORDINARY_IMPLEMENTATION — settings plumbing through
the generation manager plus HTTP-level tests with timing bounds; the concurrency design is already
in place from M17-T1 and is not changed here.

Goal:
The deep research time budget is a server setting passed from the server entry point through the
generation manager into the research run, the manager never ends a deep research reply with an
error and no reply, and server tests through POST /v1/chat (fake Ollama, fake search/read
backends, shortened budget) prove M17-AC1, M17-AC2 and M17-AC3 end to end.

Relevant Requirements:
- FR36 (.harness/requirements.md lines 267-277). AC28 edge cases at lines 535-537.

Already done in M17-T1 (read the code; do not redesign):
- `ResearchSettings` in server/src/generations/research.ts has `budgetMs` (default 480000) and
  `writeReserveFraction` (default 0.25); `runResearch` enforces the research and final deadlines
  with one cancellation signal per phase, and exports `COULD_NOT_SEARCH_NOTE`.
- shared/api.ts: `StepEventData` has optional `elapsed_ms`/`budget_ms`; `DoneEvent` has optional
  `research: { status: "complete"|"partial"|"failed"; elapsed_ms; budget_ms }`. A deep research
  done event keeps `status: "complete"` and carries `research`; a user Stop stays `cancelled`.

Acceptance Criteria:
- Setting: `GenerationManager` accepts an optional research settings override (e.g. a third
  constructor parameter or an options object — keep existing call sites compiling unchanged) and
  passes it to `runResearch`. server/src/index.ts reads an optional
  `PHONE_MODELS_RESEARCH_BUDGET_MS` (positive integer milliseconds; invalid or absent -> the
  default) and documents it in the header comment as a server setting (not test-only).
- Never an error with no reply: if `runResearch` throws for any reason other than the user's
  Stop, `runDeepResearch` appends a `content` event with a plain sentence saying the research
  failed, then a terminal `done` with `status: "complete"` and `research.status: "failed"` (with
  elapsed/budget), instead of an `error` event. The user-Stop path is unchanged (cancelled).
- HTTP tests in server/src/http/deepResearch.test.ts (extend the existing setup/fakes there),
  each sending POST /v1/chat with web true and deep_research true and reading the SSE stream:
  - AC1: with a shortened budget and a slow-but-finite step that uses up research time, the
    stream shows the run moved to writing (a `write` step) and ends with done
    `research.status: "partial"`; every `step` event of the run carries numeric `elapsed_ms` and
    `budget_ms` (budget_ms equal to the configured budget), and done carries `research` with
    `elapsed_ms` and `budget_ms`.
  - AC2: with every search failing (fake search returning failed/unavailable, no results) the
    stream ends within budget + 500 ms with done `research.status: "failed"`, content equal to
    `COULD_NOT_SEARCH_NOTE`, and the failed/unavailable search steps present in the stream.
  - AC3a: with a search that never resolves until its signal aborts (slow backend), the stream
    ends within budget + 500 ms, and the fakes record that the in-flight search received an
    aborted signal; also show an in-flight read and an in-flight model request each received an
    aborted signal at a deadline (one test per in-flight kind, or one combined test, as long as
    all three are asserted through the HTTP path).
  - AC3b: with the write model request hanging until aborted, the stream ends within
    budget + 500 ms with done `research.status: "partial"` and non-empty content (the
    gathered-notes text or `NO_REPORT_NOTE`).
  - A test that a thrown error inside the run (e.g. a web tool throwing a non-abort Error in a way
    runResearch does not absorb, or a fake that makes runResearch throw) ends with content + done
    research.status "failed" and no `error` event. If runResearch already absorbs every such
    error so that the manager path cannot be reached through HTTP, test the manager directly in
    server/src/generations/manager.test.ts instead and say so.
  Wall-time assertions measure from request send to the terminal done event. Every new test must
  finish well inside bun's default 5 s timeout (use budgets of roughly 400-1000 ms).
