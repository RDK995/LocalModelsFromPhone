TASK M19d-T2 — Deep research serves sub-questions breadth first, prefetches chosen pages in parallel while model calls stay one at a time, and ends a sub-question early when a search adds no new URLs (FR44 first half, M19d-AC1, M19d-AC2)

Routing: tier Top, model opus, reason_code DIFFICULT_CONCURRENCY — restructures the research loop's
scheduling: several page reads in flight at once under the run's one cancellation signal, while
model calls must never overlap; lifecycle of in-flight reads that are never consumed (deadline,
Stop, hard cancel), page numbering and Sources under out-of-order completion.

Goal:
Change the order in which `runResearch` (server/src/generations/research.ts) works through the plan:
1. Breadth first: every sub-question gets its searches and its FIRST page before any sub-question
   gets its SECOND page.
2. Prefetch: as soon as a page-choice ("pages") model step returns, every page it chose starts
   reading at once (in parallel), each read keeping its FR24 time limit (already inside
   webTools.read) and receiving the run's phase signal (FR36 one cancellation signal). The loop does
   NOT wait for those reads before carrying on with the next model call.
3. Model calls (every `modelStep`/`sendAttempt`) stay strictly one at a time — never two in flight.
4. A sub-question ends early (no further searches for it) when a search round adds no new URLs to
   its candidates.

Definition of terms the tests must use (this is the agreed reading of FR44):
- A sub-question "gets a page" when that page's note step happens for it: either its "notes" model
  call, or its M19c skip decision (empty/blocked). Reads may complete earlier (prefetch); that is
  not "getting" the page. So the observable breadth-first order is the order of note decisions:
  for P sub-questions, the first P note decisions are one per sub-question, in plan order, and all
  of every sub-question's round-one searches happen before any sub-question's second note decision.
- A sub-question's "first page" is the first of its chosen pages whose read succeeded and was not
  already read in this run; if a chosen read fails/returns no page, the next chosen page fills in.
- "A search round adds no new URLs": after a search, no result URL was added to that sub-question's
  candidate list (all results were already candidates, already read anywhere in the run, non-http,
  or the search returned nothing). That sub-question then runs no further searches or gap checks;
  pages it has already chosen are still noted in later rounds, and candidates it already has but has
  not chosen may still be offered to one more page choice only if its page quota is not used (your
  call — state it in your return).

Required shape (a suggested structure; equivalent designs are fine if every constraint holds):
- Keep per-sub-question state in an object (label, queue/runQueries/candidates/candidateKeys,
  searches, proposals, fallbackUsed, reads/quota, a FIFO of prefetched read promises, done flag).
- Round 1: for each sub-question in plan order: run searches as today (nextQuery, up to
  minSearches; stop searching early per item 4); then one "pages" step over its unread candidates
  choosing up to pagesPerSubQuestion; immediately start webTools.read for every chosen page
  (reserve each page's URL key in readKeys at choice time so no other sub-question chooses it) and
  push the promises onto its FIFO; then await only the FIRST successful read of its FIFO and do its
  note decision (excerpt/skip, notes step, keepNotes, T1 salvage) — then move to the next
  sub-question. While sub-question 1's remaining reads are in flight, sub-question 2's model calls
  proceed.
- Later rounds: loop over the sub-questions that are not done, in plan order, giving each at most
  ONE note decision per round: if its FIFO has a prefetched page, await it and note it; otherwise,
  if it may still search (searches < maxSearches, not ended early), run the gap check as today; if
  the gap says enough (or the step is skipped) it is done; else run its next search, and if that
  adds new URLs do a page choice for its remaining quota, prefetch, and note the first. Stop when
  every sub-question is done (quota used, maxSearches reached, ended early, gap enough, or no query).
- Preserve today's fallbacks: a skipped page-choice step reads the top unread candidates; the
  "ran out of new queries before minSearches: still read what was collected" rule.

Lifecycle and correctness constraints (each must hold; prove the starred ones in tests):
- (*) Model calls never overlap: at most one fake Ollama chat request in flight at any moment for
  the whole run.
- (*) Reads start in parallel as soon as the page choice returns: with pagesPerSubQuestion >= 2 the
  fake page backend sees two or more reads in flight at the same moment, and the first of them
  starts before the note call for that sub-question's first page and before the next model call of
  the run.
- (*) Stop (first Stop) or the research deadline with several prefetched reads in flight: every one
  of them sees its signal aborted (the run's phase signal; no per-read private signal that outlives
  the run), the run still moves to writing (deadline / first Stop) or ends `cancelled` (hard cancel
  / second Stop) promptly, as today.
- No unhandled promise rejection from a prefetched read that is never awaited (attach handling when
  the promise is created). No read is started after the research phase is over.
- FR37: page numbers are assigned by webTools.read via numberPage when a read completes, so
  prefetched pages may be numbered in completion order — that is acceptable. But every page that got
  a number must appear in the final `sources` event (absorb each completed read's events even if the
  deadline/Stop stopped the run before its note decision), numbers have no gaps, and cleanReport
  still drops citations to unread numbers. A page already read in this run is never read twice.
- FR35: raw page text of a prefetched page that is never noted is not carried into any request.
- Breadth-first ordering must also hold when some reads fail or return null pages.
- Do not change ordinary (non-deep-research) reply behaviour (FR40), settings defaults, or the
  model-step prompts/schemas except where the order of context naturally changes. No new deps.
