TASK M17-T1 — Time budget, deadline and status inside the deep research run

Routing: tier Top, model opus, reason_code DIFFICULT_CONCURRENCY — deadline timers and one
cancellation signal that must reach every in-flight search, read and model request, while telling
a deadline abort apart from a user Stop; wrong ownership hangs a run or misreports it, and is hard
to detect from a passing happy-path test.

Goal:
A deep research run (`runResearch` in server/src/generations/research.ts) has one overall time
budget, moves to writing when research time runs out, cannot overrun the budget by more than a
small margin, and ends with an answer and a run status `complete`, `partial` or `failed`, carried
on its events together with elapsed time against the budget.

Relevant Requirements:
- FR36 (.harness/requirements.md lines 267-277): one overall budget (about 8 minutes, a server
  setting), roughly a quarter reserved for writing; deadline checked before every search, read
  and model call; each search and read keeps its own FR24 time limit; one cancellation signal
  reaches every in-flight search, read and model request; when research time runs out the run
  moves to writing with what it has; always ends with a reply whose status is `complete`,
  `partial` or `failed`; `failed` = no usable material (e.g. every search backend unavailable),
  answer is a plain sentence saying the research could not search, plus any steps; never hangs,
  never ends with an error and no reply.
- FR24 (line 146), FR33 (line 222, the no-answer note idea), FR35/FR37 (unchanged behaviour).

Acceptance Criteria (this task proves them at the research-module level; M17-T2 proves them again
through POST /v1/chat):
- AC1: the deadline is checked before every search, read and model call; when research time
  (budget minus the writing reserve) runs out the run moves to writing with what it has and ends
  `partial`; the run's events carry its status and elapsed time against the budget.
- AC2: with every search failing (webTools.search returns no results / failed or unavailable
  steps) the run ends within budget + small margin as `failed`, with a plain sentence saying the
  research could not search as its content, plus its steps.
- AC3: with a slow search backend (search that only resolves when its signal aborts, or after a
  long delay) the run ends within budget + small margin; the in-flight search, read and model
  request each receive an aborted signal at the deadline; with the deadline hitting during the
  write-up the run ends within budget + small margin as `partial` with a non-empty answer (the
  existing gathered-notes text or NO_REPORT_NOTE if nothing).

Design decisions already taken (follow them; do not redesign):
1. Settings. Add to `ResearchSettings` and `DEFAULT_RESEARCH_SETTINGS`:
   `budgetMs` (default 480_000) and `writeReserveFraction` (default 0.25). Research deadline =
   start + budgetMs * (1 - writeReserveFraction); final deadline = start + budgetMs.
2. Signals. Inside the run derive one research-phase signal = AbortSignal.any([user signal,
   research-deadline signal]) and one write-phase signal = AbortSignal.any([user signal,
   final-deadline signal]). Every `client.chat`, `webTools.search` and `webTools.read` call gets
   the signal for its phase. Deadline timers are created by the run and always cleared in a
   `finally` (no timer may keep the process or a test alive). Use setTimeout + AbortController
   (or AbortSignal.timeout) — either is fine as long as it is cleared/unreferenced.
3. Checks. Before every search, read and model call, check the phase deadline; if research time
   is over, stop researching (no further searches/reads/model steps in the research phase) and go
   to writing. If the final deadline has passed before the write call, skip the write call.
4. Telling aborts apart. A user Stop (opts.signal aborted) keeps today's behaviour exactly: done
   with status "cancelled". A deadline abort is NOT a cancellation: an AbortError thrown by an
   in-flight search/read/model call because of the research deadline moves the run to writing; one
   thrown during the write because of the final deadline ends the run with the fallback answer.
   modelStep must not retry after a deadline abort.
5. Status, decided at the end:
   - `failed`: at least one search was attempted, no search in the run returned any result, and
     no page was read. Content is exactly this plain sentence, exported as a constant
     `COULD_NOT_SEARCH_NOTE`: "The research could not search the web — every search failed or was
     unavailable. Try again later." The write model call is skipped. Steps already emitted stay;
     the sources event follows the existing rule (emitted when searchesRun > 0).
   - `partial`: the research deadline cut the research phase short, or the final deadline hit
     before/during the write-up, or the write step produced no report (fallback text used).
   - `complete`: otherwise.
   The content event is always emitted with non-empty text before done (existing fallback chain:
   cleaned report -> gathered notes -> NO_REPORT_NOTE).
6. Events. In shared/api.ts add optional fields (backward compatible; ordinary replies unchanged):
   - `StepEventData`: `elapsed_ms?: number; budget_ms?: number;` — every step event the run
     yields (its own plan/write steps and the search/read steps it absorbs from web tools) carries
     both, elapsed measured from the run's start.
   - `DoneEvent`: `research?: { status: "complete" | "partial" | "failed"; elapsed_ms: number;
     budget_ms: number }`. A deep research run's done event keeps `status: "complete"` (the reply
     ended with an answer) and carries `research`. The user-Stop path keeps `status: "cancelled"`
     and may omit `research`.
7. The run never throws for a deadline. It may still throw if the user signal is aborted (as
   today) — the manager turns that into cancelled.
