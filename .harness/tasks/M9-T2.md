4. `systemNote(now)` returns a short system-message string containing the date as ISO `YYYY-MM-DD` of `now` (local time) and the weekday/month in words, telling the model it may use web_search and read_page for current information and should cite what it used.
5. `execute` for `web_search`: POST `${baseUrl}/v1/search` JSON `{query, max_results: 5}`. Events, in order: step `{kind:"search", status:"started", query}` then the same `step_id` with final status: 200 -> `done` (plus one `source` event per result `{title,url}`), toolResult = numbered list of title, url, snippet (and a clear "no results" text if empty); 503 search_unavailable -> `unavailable`, detail = error code; any other non-2xx, network error, or client timeout -> `failed`, detail = error code or "timeout"/"network_error". On failure/unavailable the toolResult tells the model the search failed/was unavailable and that it should answer from what it has.
6. `execute` for `read_page`: POST `${baseUrl}/v1/read` JSON `{url}`. step `{kind:"read", status:"started", url}` then final: 200 -> `done` plus one `source` `{title, url: final_url}`, toolResult = title, final_url and the markdown, with an explicit note when `truncated` is true; 400/415/502/504/network/timeout -> `failed` with detail = the service's `error` code (e.g. blocked_destination) or "timeout"/"network_error"; toolResult says the page could not be read and why.
7. step_id is unique per step (e.g. crypto.randomUUID()).
8. Unknown tool name or missing/non-string argument -> no HTTP request, no step event, toolResult explains the error to the model.
9. Timeout/abort: each request uses AbortSignal.any([signal, AbortSignal.timeout(timeoutMs)]) (or equivalent). If the CALLER's `signal` aborts, `execute` rejects (throws the abort reason / an AbortError) — this is the only rejection. A client timeout is NOT a rejection; it becomes a `failed` step with detail "timeout".
