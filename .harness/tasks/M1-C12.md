Defect (diagnosed by the orchestrator from the human's 15:51 on-phone evidence and the code):
mobile/src/app/_layout.tsx reads the token ONCE at launch into `hasToken` and declares
Stack.Screen "chat"/"settings" only when a token existed at launch, "setup" only when it did not.
On a first-time launch (no token) the user is on Setup; setup.tsx saves the token and calls
`router.replace("/chat")`, but RootLayout's `hasToken` is still false, so "chat" and "settings"
are NOT declared screens and their options (chat `headerShown: false`, titles) never apply.
Result, exactly as the human saw at 15:51: Chat shows two top bars (a default Stack header titled
with the raw route name "chat" above Chat's own header), Settings shows "< chat" / "settings", and
because chat.tsx's KeyboardAvoidingView uses keyboardVerticalOffset={0} on the premise that its
Stack header is hidden, the view falls short by the header height and the keyboard covers the
message box. The same happens after logout (settings/chat -> /setup with hasToken still true).
Routing by token is already done by mobile/src/app/index.tsx (Redirect via initialRoute) and by
the screens' own router.replace calls, so RootLayout does not need to gate screens.
