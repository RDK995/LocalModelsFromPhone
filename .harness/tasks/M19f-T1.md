TASK M19f-T1 — The app's 300 s resume allowance applies per outage and resets after every successful resume (M19f-AC2)

Routing: tier Mid, model sonnet, reason_code ORDINARY_IMPLEMENTATION — a small change to who owns the
resume budget clock in the app server client's drop/resume loop; clear oracle via the client's
injectable fake clock/sleep and scripted dropping streams.

Requirement (FR45, .harness/requirements.md line ~351): "the app's 300 s resume allowance applies per
outage (reset after every successful resume) rather than to the whole reply". Applies to every reply
(deep research, ordinary web, switch off) — the client loop is shared.

Acceptance criterion M19f-AC2 (verbatim): "App tests through the app server client with scripted
dropping streams: the 300 s resume allowance applies per outage and resets after every successful
resume, so several short outages in one reply all resume; a single outage longer than 300 s ends the
reply on the phone with error status and its steps kept."

Context (current code, mobile/src/api/client.ts):
- `chat()` main loop (~lines 538-597) holds `let firstDropAt: number | null = null;`. On a drop it sets
  `firstDropAt = this.nowImpl()` only when it is null (or on a foreground drop), then calls
  `resumeStream(...)`; on success it does `firstDropAt = resumed.firstDropAt;`. So the 300 s budget
  (`RESUME_BUDGET_MS`, mobile/src/api/resume.ts) is measured from the FIRST drop of the whole reply:
  a reply with several short outages spread over > 300 s fails on a later outage. This is the bug.
- `resumeStream()` (~lines 775-890) checks `this.nowImpl() - firstDropAt > RESUME_BUDGET_MS`; it also
  restarts `firstDropAt` on foreground events (M4c behaviour — keep that unchanged).
- A "successful resume" = `resumeStream` returned `{ outcome: "response" }` (a 200 events response).
  After it, the outage is over: the next drop must start a fresh 300 s allowance measured from that
  drop. Keep the backoff attempt counter per outage as it is today (it is already local to
  resumeStream).
- The client takes `clock: { now, sleep }` (see `nowImpl`/`sleepImpl`, ~line 287-295); existing tests
  in mobile/src/api/client.test.ts `describe("APIClient dropped-connection resume (FR11)")` (~line 896)
  use a fake sleep/clock pair (helpers ~line 748) and include "(i) stops and reports an error once the
  resume budget is exhausted" (~line 1367). Reuse those helpers and scripted streams.
- mobile/src/chat/conversationSession.ts `sendInConversation` persists the reply on onError via
  `persistReply("error")`, including `accumulator.steps`. Tests for it are in
  mobile/src/chat/conversationSession.test.ts.
