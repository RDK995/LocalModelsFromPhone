TASK M18-T1 — The server reports the configured deep-research model and refuses deep research it cannot run

Routing: tier Mid, model sonnet, reason_code ORDINARY_IMPLEMENTATION — one new server setting
threaded to GET /v1/state and two request refusals on POST /v1/chat, with HTTP-level tests; no
concurrency or research-loop changes.

Goal:
The deep-research model name is a Mac-side server setting (default `qwen3.5:35b-a3b`) that
GET /v1/state reports to the app; POST /v1/chat refuses a deep research request when web is off or
when the requested/resident model is not the configured deep-research model, with a plain error and
no run started; and a test proves the chat model is never offered a `deep_research` tool.

Relevant Requirements:
- FR34 (.harness/requirements.md lines 241-251). Read it in full.
- Milestone M18 criterion M18-AC1 (.harness/milestones.md, section "## M18").

Acceptance Criteria:
- Setting: server/src/index.ts reads an optional env var `PHONE_MODELS_RESEARCH_MODEL` (trimmed,
  non-empty; absent/blank -> default `qwen3.5:35b-a3b`), documented in the header comment next to
  `PHONE_MODELS_RESEARCH_BUDGET_MS` as a server setting. Export a small parse function
  (e.g. `parseResearchModel`) with a unit test in server/src/index.test.ts, mirroring how
  `parseResearchBudget` is done and tested. Define the default as one exported constant on the
  server side (the only place the name is hardcoded).
- The setting is passed into `createServer` (add an optional option, e.g. `researchModel`, to
  `CreateServerOptions`; when omitted it uses the default) — existing call sites and tests keep
  compiling unchanged.
- shared/api.ts: `StateResponse` gains `deep_research_model: string` (documented: FR34, the
  configured deep-research model name reported by the server). GET /v1/state includes it. Prefer
  adding it in the HTTP handler or ModelManager, whichever keeps existing tests unchanged; any
  existing test that deep-equals the whole state body may be updated ONLY to add this field.
- POST /v1/chat with `deep_research: true`:
  - and `web` not `true` -> refused, HTTP 400 or 409, JSON error body with a code
    `deep_research_needs_web` and a plain message (e.g. "Deep research needs web search to be on");
    no generation starts (GET /v1/state shows `generation: null`, no Ollama chat call made).
  - and `model` (which the handler already checks is resident) is not the configured
    deep-research model -> refused, HTTP 409, code `deep_research_model_not_loaded`, message
    "Load <configured model name> to use deep research"; no generation starts.
  - and web on and the configured model resident -> behaves exactly as today (existing deep
    research tests in server/src/http/deepResearch.test.ts keep passing). Existing tests that use a
    different fake model name for deep research may pass `researchModel` to `createServer` to match
    their fake model, rather than being weakened.
  - `deep_research` absent or false -> unchanged behaviour.
- Ordering: the new refusals happen after body parsing and before any generation starts; keep the
  existing busy/in-flight/resident checks as they are.
- Test proving no `deep_research` tool: assert that the tool definitions the web tools offer the
  chat model (server/src/web/tools.ts lines ~76-105) contain no tool named `deep_research`, and
  through POST /v1/chat with web on (no deep_research) that the request the fake Ollama received
  lists tools whose names do not include `deep_research`.
- Tests for each refusal go through the real HTTP entry point (createServer + fetch), following
  the patterns in server/src/http/deepResearch.test.ts and server/src/http/server.test.ts.
