# Turn off hidden thinking to finish research

The run failed because of the model's hidden "thinking", not because of the web. The deep-research loop sends `think: true` with no output cap on every step ([research.ts:64-77, 336-352](server/src/generations/research.ts)). At about 45 tok/s, a 40–100 s tool decision works out to roughly **1,800–4,500 generated tokens**, nearly all of them thinking. The planning phase took 1:54 on two tiny prompts, so prompt reading cannot explain it. The fix comes in four parts, in this order. **First, log Ollama's per-call timings**, so that every later change is measured rather than guessed. **Second, turn thinking off for the routine steps** (query proposal, page selection, note-taking, gap check) and give them small output caps; a live probe on this Mac already showed `format` holds with thinking off (7/7 valid). **Third, send the note call 2–3K tokens of the most relevant passages instead of a page of up to 40,000 characters.** **Fourth, take the clock and liveness off the model's critical path**: emit a step before every model call, send an SSE heartbeat, tick the phone clock locally, reset the resume budget after each successful resume, and render a reply's error status instead of an empty bubble. Together these should bring a routine call from 40–100 s to roughly 5–15 s. That fits the default plan of about 18 calls into the 6-minute research phase with time to spare, which is what AC29's "at least 3 distinct cited pages" needs. Every change in the first two tiers fits FR34–FR40 as written. Six later or optional changes need a requirement amended: snippet-only notes, a merged brief-and-plan call, code-chosen pages, looser quote matching, an MLX model tag, and a global context-length setting.

## Two tiny prompts took 114 seconds, which points at thinking, not reading

The code map puts the observed heat-pump run in its timeline ([current_codebase notes, Q1](server/src/generations/research.ts)). Between 0 and 113.6 s there were two model calls, brief and plan, each over a short prompt. Next came about 44 s for a query-proposal call, then ~2 s for a second search, which took no model call. Then about 99 s went on a "select pages" call plus one read. The service limits a read to 15 s ([fetchPage.ts:12-13, 88-90](search/src/fetch/fetchPage.ts)). The last ~102 s went on a note call over that one page, which the research deadline killed at 360 s (480 s × 0.75). The deadline throws away partial output ([research.ts:366-369](server/src/generations/research.ts)), so zero notes survived. The code marks a run `failed` whenever searches ran but no notes exist, whatever the cause ([research.ts:562](server/src/generations/research.ts)). So the phone was told the pages could not be used, when **the run had simply run out of time inside its first note call**, on sub-question 1 of 3. Web I/O was a rounding error. Searches took about 2 s and reads at most 15 s. Model calls took everything else.

The arithmetic decides between the two candidate bottlenecks. The earlier report in this series argued that on a Mac "the bottleneck is prefill", meaning reading the prompt ([llama.cpp #4167](https://github.com/ggml-org/llama.cpp/discussions/4167)). That holds when prompts are large and outputs short. Here the plan calls carry almost no prompt. Ollama measured this model's prefill at about **1,150 tok/s even on its older llama.cpp backend** on an M5 Max ([Ollama blog: MLX](https://ollama.com/blog/mlx)). An M1 Max is slower, but a few hundred tokens of prompt still cost seconds, not minutes. Generation is what eats time. Qwen3.5 thinks by default, and its model card suggests output budgets of **32,768 tokens for most queries** ([Qwen3.5-35B-A3B card](https://huggingface.co/Qwen/Qwen3.5-35B-A3B)). Nothing in this code caps that. Per token, thinking costs the same as answering ([Kapetanovic benchmark](https://antekapetanovic.com/blog/qwen3.5-apple-silicon-benchmark/)), so the only lever is how many thinking tokens are produced.

Two facts in the repository argue for caution, and both are reasons to measure first. In the M16 live run, `done` reported only **2,352 eval tokens at 35.4 tok/s over a 1,433 s run** ([M16-T5-live.log](.harness/evidence/M16-T5-live.log)). That is about 66 s of decoding, which would make decoding a small share of the time if `eval_count` covered every call and every thinking token. The code sums `eval_count` but never logs `load_duration` or `prompt_eval_duration` ([research.ts:360-362](server/src/generations/research.ts)), so the remaining time is unaccounted for. The second fact is that the run may reload the model when it starts. The model is loaded and chatted with without `num_ctx` ([client.ts:179-201](server/src/ollama/client.ts)), but research calls send `num_ctx: 32768`, and changing the context size forces Ollama to rebuild the runner ([Ollama FAQ](https://docs.ollama.com/faq)). A reload of 24 GB of weights would inflate the first call, which is the 1:54 planning phase. No reload time has been measured. Neither fact changes the recommendation, because thinking-off and smaller inputs help whichever cost dominates. They do change the order of work: **instrumentation comes first, because it settles the split in one run.**

## The ranked changes, with the time each should buy back

The table below is the recommended order. The savings are estimates from token arithmetic at the observed 45 tok/s, not measurements, and each row names the live check that confirms or refutes it. "Routine call" means query proposal, page selection, note and gap check.

| 1 | `think: false` plus a `num_predict` cap and model-card sampling for the routine steps | Each routine call from 40–100 s to about 5–15 s; about 4–8 min saved on a full run | Somewhat worse queries and selections; `format` regressions on some Ollama versions | Thinking length = 0; routine call p50 < 10 s, p95 < 25 s; schema validity ≥ 95% | Fits FR35 (it does not mandate thinking) |
| 2 | Hard per-call wall-clock cap; thinking on plan and write only, with a fallback to non-thinking | Caps the worst case at about 30–45 s per call; planning from 114 s to about 20–40 s | Thinner plans if the cap trips often | Plan phase < 40 s; count of fallbacks per run | Fits FR35/FR36 |
| 3 | BM25-ranked excerpt of about 2–3K tokens per page for the note call, and skip pages with no matching passage | Prefill per note drops about 3–4×; fewer wasted note calls | Missing a relevant passage that BM25 ranks low | `prompt_eval_count` per note < 4K; notes kept per page | Fits FR35/FR37 (quote still checked against full page text) |

### Rank 0: measure before changing anything

Ollama returns `load_duration`, `prompt_eval_count`, `prompt_eval_duration`, `eval_count` and `eval_duration` on the final chunk of every call. Thinking text arrives separately in `message.thinking` ([Ollama docs: Thinking](https://docs.ollama.com/capabilities/thinking)). Log one structured line per call with the step name, the `think` setting, the attempt number, the wall time and those fields. Add the character count of the thinking, which `modelStep` already receives and discards ([research.ts:357-376](server/src/generations/research.ts)). Then run the heat-pump question once, unchanged, as the baseline. This settles three open questions in a single run: whether the first call pays a reload, how much of each call is prefill and how much is generation, and how many thinking tokens each step really produces.

The reload has a cheap fix: when the research model is warmed, send it the same `num_ctx` the research calls use. Ollama rebuilds the runner whenever the context size changes ([Ollama FAQ](https://docs.ollama.com/faq)). A global `OLLAMA_CONTEXT_LENGTH=32768` in the LaunchAgent would also stop the reload, but it would change the context window of ordinary replies, which touches FR40. If the owner wants that route, FR40 needs an explicit note. Sending `num_ctx` only from research calls and from the research model's warm-up avoids the question.

### Rank 1: thinking off for every routine step

The `think` field is set per request on `/api/chat` and does not reload the model ([Ollama docs: Thinking](https://docs.ollama.com/capabilities/thinking)). Turning it off for routine steps is the biggest and safest win. A 300-token answer without thinking takes about 7 s at 45 tok/s, while a 3,000-token thinking call takes about 67 s, which matches the observed 40–100 s range. The quality cost is real but bounded. In third-party measurements on the Qwen3 family, thinking added about **8 points on BFCL v3 (70.4 vs 62.8 for Qwen3-32B)** and more on multi-turn tau-bench ([Klear-AgentForge, arXiv 2511.05951](https://arxiv.org/pdf/2511.05951)). Writing one search query or picking from five URLs is a single-shot decision, closer to BFCL than to tau-bench, so the gap should sit at the small end. No Qwen3.5-specific comparison exists, and the live check is how this codebase finds out.

Three details matter in the implementation. First, use top-level `think: false` on `/api/chat`, never `options.think` or `/api/generate`. Ollama ignored thinking-off for qwen3.5 on `/api/generate` and spent the whole `num_predict` on thinking ([ollama#14793](https://github.com/ollama/ollama/issues/14793)). Downstream projects have shipped "think: false" settings that were never forwarded to the request ([openclaw#71088](https://github.com/openclaw/openclaw/issues/71088)), so the check must read `message.thinking` and confirm it is empty, not just trust the setting. Second, `format` with thinking off has its own history: Ollama 0.17.6 ignored the schema in exactly that combination ([ollama#14645](https://github.com/ollama/ollama/issues/14645)). That was fixed, and this Mac's own M16 probe found **think-off 7/7 valid** on the installed setup ([M16-T4-probe.json](.harness/evidence/M16-T4-probe.json)). The Mac now runs Ollama 0.32.14, so re-run the probe after any upgrade. Third, a `num_predict` cap is safe only when thinking is off. With thinking on, thinking can use up the whole cap and leave an empty answer ([ollama#14793](https://github.com/ollama/ollama/issues/14793)). Suggested caps are about 200 tokens for queries, selection and gap check, and about 800 for notes (five notes, quotes under 300 characters). Use the model card's non-thinking sampling (temperature 0.7, top_p 0.8, top_k 20) as the starting point ([Qwen3.5-35B-A3B card](https://huggingface.co/Qwen/Qwen3.5-35B-A3B)). Ollama's structured-output docs prefer a lower temperature for schema calls ([Ollama structured outputs](https://docs.ollama.com/capabilities/structured-outputs)), so try 0.3 on the select and gap steps and keep whichever validates better.

### Rank 2: a wall-clock cap on every call, and thinking only where it pays

Ollama has no thinking budget. `think` takes only a boolean or a named level, never a number ([Ollama docs: Thinking](https://docs.ollama.com/capabilities/thinking)). llama.cpp has a real reasoning budget, but this codebase runs only Ollama ([Olivier Chafik on X](https://x.com/ochafik/status/1927043808501387703)). So build the budget from time. Give every routine call a hard cap of about 30 s; open_deep_research uses the same pattern with a **60 s per-page summarization timeout** that falls back to raw content ([utils.py](https://raw.githubusercontent.com/langchain-ai/open_deep_research/main/src/open_deep_research/utils.py)). For the steps where reasoning helps, the plan and the final report, keep thinking on, but stream it. If the thinking passes about 20–30 s (roughly 900–1,350 tokens), abort and re-issue the request with `think: false`. Brief and plan without thinking are short outputs and should take seconds. If plan quality drops on the live questions, turn thinking back on for the plan alone under the guard. The write step keeps thinking. Its reserve is 120 s, and a ~1,200-token report takes about 27 s to decode, so the guard can allow 45–60 s of thinking and still finish in time. A badly tuned budget hurts accuracy, and one secondary source cites HumanEval falling from 94% to 78% ([aihaven summary](https://aihaven.com/news/llama-cpp-reasoning-budget-update/)). That is why the cap falls back to a non-thinking answer instead of truncating one.

### Rank 3: send passages, not pages

Today the note call gets the whole extracted page, up to **40,000 characters (about 10K tokens)**, plus the brief, the plan and the notes ([extract.ts:8, 44-48](search/src/extract/extract.ts); [research.ts:491-498](server/src/generations/research.ts)). That costs prefill time. It also costs accuracy: QA accuracy falls when the relevant text sits in the middle of a 4K–16K-token context ([Liu et al., Lost in the Middle](https://cs.stanford.edu/~nfliu/papers/lost-in-the-middle.arxiv2023.pdf)). Every mature agent filters first. crawl4ai ranks chunks with BM25 against the user's query ([crawl4ai Fit Markdown](https://docs.crawl4ai.com/core/fit-markdown/)). GPT-Researcher filters chunks by embedding similarity at 0.42 ([GPTR config](https://docs.gptr.dev/docs/gpt-researcher/gptr/config)). Perplexica splits pages into 4,000-character chunks and extracts from each ([baseSearch.ts](https://github.com/ItzCrazyKns/Perplexica/blob/master/src/lib/agents/search/researcher/actions/search/baseSearch.ts)). The recipe for this server: split the markdown on headings and paragraphs into passages of about 150–400 words, and score them with a small TypeScript BM25 against the sub-question plus the main question's terms. Keep the title, the first paragraph and the top 4–8 passages, about 2–3K tokens in all. Put the page text first and the task last ([Anthropic long-context tips](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/long-context-tips)). When no passage clears the threshold, skip the note call entirely, which saves a call on pages that are off-topic. This needs no amendment. Quotes are still checked against the stored full page text, raw text is still discarded once noted, and the model still sees only the current page.

Two smaller fixes belong in the same change. The `pageText` variable is dead code ([research.ts:491](server/src/generations/research.ts)). Pages whose extracted text is tiny, or that show challenge markers, should be logged as "blocked" or "empty" and skipped without a model call. Cloudflare now blocks AI crawlers by default on new domains ([Cloudflare blog](https://blog.cloudflare.com/content-independence-day-no-ai-crawl-without-compensation/)), and Readability-style extractors return nothing below 500 characters by design ([mozilla/readability](https://github.com/mozilla/readability)). Trafilatura scores F1 0.926 against Defuddle-class tools on its benchmark ([trafilatura evaluation](https://trafilatura.readthedocs.io/en/latest/evaluation.html)). But extraction quality did not cause this failure, so a switch of extractor can wait for the empty-page counts from rank 0.

## The phone went blank because the stream went quiet

The frozen clock is by design and is easy to fix. The app sets its clock only when a step event arrives ([streamReducer.ts:45-58](mobile/src/ui/streamReducer.ts)), and nothing ticks locally ([chatItems.ts:97, 106-109](mobile/src/ui/chatItems.ts)). The server emits `plan started` at 0 ms and nothing else until `plan done` at 113.6 s. Search and read events are built inside the web tools, but they are only yielded after each await returns, so "started" and "done" carry the same timestamp ([tools.ts:133-149, 171-182](server/src/web/tools.ts); [research.ts:383-392](server/src/generations/research.ts)). Query proposal, selection, note and gap calls emit no step at all. Three changes fix it. First, the app ticks every second from the last server `elapsed_ms` plus local time since it arrived, capped at the budget, and re-anchors on every event and after every resume. Second, the server yields "started" steps before awaiting, and adds steps for the model calls, labelled for example "Choosing pages", "Taking notes: <domain>" and "Checking for gaps". Third, a heartbeat. FR36 already asks for live phases and "3:12 of 8:00", so all three close a gap in the existing requirement rather than add to it.

The empty bubble most likely came from a lost stream, not from the server's failure message. The server did emit the failure sentence and `research.status: "failed"` at about 360 s. Had the app received them, it would have shown the sentence and "Deep research: failed" ([chat.tsx:390-395, 432-458](mobile/src/app/chat.tsx)). It showed neither, and also no read step (emitted at 258 s). That places the loss between about 160 s and 258 s. The code then explains the blank. The SSE stream sends one `: connected` comment and then nothing during model calls ([server.ts:333-350](server/src/http/server.ts)), so gaps of 44–102 s are silent. The app's resume budget is **300 s from the first drop and is never reset after a successful resume** ([client.ts:561-595, 812-837](mobile/src/api/client.ts); [resume.ts:29-35](mobile/src/api/resume.ts)), so several drops in one long run share one five-minute allowance. When it runs out, the reply is saved as `status: "error"` with whatever content had arrived. A deep-research reply's content arrives only at the very end, so that is nothing ([conversationSession.ts:199-202](mobile/src/chat/conversationSession.ts)). `buildChatItems` never reads the message status, so an error reply with empty content renders as an empty bubble ([chatItems.ts:34-70](mobile/src/ui/chatItems.ts)). The repository does not record whether Tailscale Serve or the iOS network stack actually cut the idle stream. Reading the saved message's `status` from the device would confirm this explanation in a minute.

The fixes do not depend on confirming it. Send an SSE comment heartbeat every 15 s. Comments carry no event ID, so `Last-Event-ID` resume and the no-gaps, no-duplicates rule (FR38) are untouched, and a 15 s heartbeat also stays far inside Bun's 255 s `idleTimeout` ([server.ts:666](server/src/http/server.ts)). Reset `firstDropAt` after every successful resume, so the 300 s applies to each outage, not to the whole reply. Render the status: an `error` reply with no content should show a line such as "Lost connection to the Mac before the report arrived", with its steps expanded. Finally, change the server's failure sentence when the cause was time. `COULD_NOT_READ_NOTE` claims the pages were unusable ([research.ts:97-103, 585](server/src/generations/research.ts)), which was false here. A third sentence, "The research ran out of time before it could take notes", is accurate and needs no amendment. FR36 asks only for a plain sentence. To verify, start a run, toggle airplane mode for 30 s twice, and confirm the phone shows the steps and the final text or status. The clock should never stall for more than a second.

## Fitting 18 calls into six minutes, and where the requirements bend

Once ranks 1–3 land, the default plan becomes a budget sum rather than a hope. Count about 2 planning calls, then for each of 3 sub-questions one query call, one select call, up to two note calls and one gap call, and finally one write. That is **about 18 calls** ([research.ts:399-583](server/src/generations/research.ts)). At 5–15 s per routine call plus ≤15 s reads, the research phase needs about 2–4 minutes of the 6 available. That leaves room for the second round of searches the gap check asks for. Two scheduling changes protect the AC29 target of three distinct cited pages, even when calls run slower than estimated. **Go breadth-first**: give every sub-question its searches and first page before any sub-question gets a second page, so a short run still covers the whole plan. **Prefetch reads**: start the chosen pages' fetches in parallel the moment selection returns, so the next page's fetch runs while the model takes notes on the current one. Perplexica and GPT-Researcher both fetch pages in parallel ([baseSearch.ts](https://github.com/ItzCrazyKns/Perplexica/blob/master/src/lib/agents/search/researcher/actions/search/baseSearch.ts); [GPTR config](https://docs.gptr.dev/docs/gpt-researcher/gptr/config)). Keep model calls strictly serial. With `OLLAMA_NUM_PARALLEL` above 1 on Apple Silicon, each request slowed from about 22 to 10 tok/s for a 1.8× aggregate gain at best ([jangwook.net experiment](https://jangwook.net/en/blog/en/local-llm-concurrent-requests-num-parallel-experiment/)). That trade is wrong for a single sequential loop. Also end a sub-question early when a search round adds no new URLs, and when the deadline cuts a note call, parse whatever complete notes the partial JSON already holds instead of discarding it. Moving the per-step task text from the system message to the end of the user message makes the prefix byte-stable, so Ollama's prefix cache can reuse it ([Ollama blog: MLX](https://ollama.com/blog/mlx)). The saving is small once prompts are short.

Several tempting shortcuts cross an agreed line, and each needs an explicit amendment before it is built. A **snippet-as-note fallback** is the most valuable of them. Perplexica's fast modes and local-deep-researcher's default both treat the search snippet as the note when a page cannot be read ([baseSearch.ts](https://github.com/ItzCrazyKns/Perplexica/blob/master/src/lib/agents/search/researcher/actions/search/baseSearch.ts); [local-deep-researcher utils.py](https://raw.githubusercontent.com/langchain-ai/local-deep-researcher/main/src/ollama_deep_researcher/utils.py)). That would make an all-pages-blocked run end `partial` instead of `failed`. But FR35 and FR37 require notes to carry a verbatim quote from a read page, and FR37 makes the Sources list the pages read, so a snippet note breaks both. **Merging brief and plan into one call** saves one call. FR35 lists them as separate steps, so it needs at least a clarification. **Choosing pages in code** by ranking the snippets with BM25 would remove the select call. FR35 says only "choose pages from the URLs the server parsed" and does not say who chooses, but the agreed reading is a model step. **Matching quotes despite markdown** would rescue notes the model copied without `**` or link syntax ([research.ts:499-505](server/src/generations/research.ts)), but FR37 specifies whitespace normalisation only. **Dropping to one search per sub-question** directly contradicts FR35's "more than one query". **A headless re-fetch for script-rendered pages** is on the deferred list ([requirements.md:482-485](.harness/requirements.md)).

The largest raw speed-up is also the riskiest. Ollama's MLX backend roughly **doubled decode (58 → 112 tok/s) and raised prefill 1.6× for this model** on an M5 Max ([Ollama blog: MLX](https://ollama.com/blog/mlx)). It uses separate tags, for example `qwen3.5:35b-a3b-nvfp4`; the default `qwen3.5:35b-a3b` tag in use is GGUF ([ollama.com tags](https://ollama.com/library/qwen3.5/tags)). In Ollama 0.32.0, however, `format` is **silently ignored on MLX models**: the request returns 200 with prose ([ollama#17183](https://github.com/ollama/ollama/issues/17183)). FR35 makes the JSON schema the contract for every step, so moving to MLX means amending FR35 to "prompted JSON validated by code". It also means re-measuring on the M1 Max, since no source gives MLX figures for this chip, and changing the configured model setting. Leave it until ranks 0–5 are measured. If they already deliver runs well inside 8 minutes, the gain is not worth the lost guarantee.

The verification plan follows AC29 itself. Build a fixed set of four questions: the heat-pump question that failed plus the three AC29 questions. After rank 0, run the set once as a baseline and keep the per-call logs. After each later rank, run the set again and record five numbers per run: total wall time, research-phase calls completed, distinct pages read, notes kept, and the routine-call p50/p95 latency. Ranks 1–3 should together produce **routine p50 under 10 s, planning under 40 s, at least 3 distinct cited pages per run, and every run ending `complete` or `partial` within 8:00 plus margin**. AC28's fake-backend tests need matching updates: assert the `think` value and the `num_predict` cap per step, the excerpt size sent to note calls, the timing of step and heartbeat events, and the error-status rendering.

## Conclusion

The pipeline's shape was right, a fixed, code-owned sequence of small schema-constrained calls, and the open-source survey confirms it as the design that both bounds time and tolerates local models. What broke was one default. Thinking was turned on for every step because a probe showed it produced valid JSON. The probe measured validity and never measured cost. On a reasoning model, thinking is the one setting that sets the price of every call, so it needs a per-step budget like time and context already have. The lesson for this codebase's harness is that live probes must record latency next to correctness, and the per-call log from rank 0 makes that the default from now on.

The blank bubble shows a related blind spot. Both the server and the app were built to report events, and the long model calls produced none, so silence looked the same as failure. Heartbeats, a local clock, a visible error status and per-outage resume budgets would make the phone honest even on a slow run, and none of them waits on the speed work. These display fixes can ship first, which also makes the speed experiments easier to watch from the phone.
