# Let code drive the research loop

The deep-research techniques that hold up on open-weight, locally hosted models are the ones where **code owns the control flow and the model makes only small, schema-constrained decisions**. In practice that means a fixed plan, then search, read and extract, then a check for gaps, run inside hard budgets. Context stays bounded because the model works from a rolling notes or report state, not a growing transcript. Citations are assigned by the server, never typed by the model. The reasons are measurable. Open models such as Qwen3-32B make **fewer than 2 search calls per question even when prompted**, where GPT-5 makes more than 20 ([BrowseComp-Plus](https://arxiv.org/html/2508.06600v1)). Ollama's native tool-calling path has had repeated template and parser bugs for exactly the Qwen3 and gpt-oss models you would run ([ollama#14601](https://github.com/ollama/ollama/issues/14601), [ollama#11781](https://github.com/ollama/ollama/issues/11781)). And every model tested degrades as input grows, with even one distractor hurting ([Chroma Context Rot](https://www.trychroma.com/research/context-rot)). For this server, `deep_research` should be a separate tool that the chat model calls with a question and an effort level. It runs as a sequential, deadline-checked sub-loop on the one resident model, emits the existing step and source events, and **always returns a report object marked `complete`, `partial` or `failed`**, never an exception and never a hang. Expect a standard run to take about 5 minutes on an M4 Max-class Mac. The best local model candidates are the Qwen3.5-35B-A3B and 30B-A3B-family mixture-of-experts models (a few billion parameters active per token) on Macs with 32 GB or more. All vendor benchmark numbers in this report are upper bounds, because nobody has published how these models score once quantized and run locally.

## Small open models under-search and break on tool templates, so the loop belongs in code

Open systems use six recurring loop designs. The simplest is a fixed query, search, summarize and reflect loop (local-deep-researcher, built for Ollama, **3 loops by default**) ([local-deep-researcher](https://github.com/langchain-ai/local-deep-researcher)). Next are plan-then-execute (GPT-Researcher's planner and executor agents) ([gpt-researcher](https://github.com/assafelovic/gpt-researcher)) and a supervisor with isolated sub-researchers (open_deep_research) ([LangChain blog](https://www.langchain.com/blog/open-deep-research)). Then come outline-first writing (STORM) ([storm](https://github.com/stanford-oval/storm)) and a single-agent ReAct loop over a fixed menu of actions (Jina, II-Researcher, MiroThinker) ([Jina guide](https://jina.ai/news/a-practical-guide-to-implementing-deepsearch-deepresearch/)). The last is round-based "workspace reconstruction", where each round rebuilds a small working context around an evolving report (IterResearch, WebResearcher, Tongyi Heavy mode) ([IterResearch](https://arxiv.org/abs/2511.07327); [Tongyi blog](https://tongyi-agent.github.io/blog/introducing-tongyi-deep-research/)). With one resident model and one reply at a time, the "parallel" designs run in sequence anyway. What they still offer is **context isolation**: each sub-question gets a fresh, small context and hands back a compressed answer. That benefit is real. LangChain found that a single agent on multi-topic requests suffered "context clash". It also found that parallel section writers produced disjoint reports, so multi-agent work belongs in the research phase only, with one final write-up ([LangChain blog](https://www.langchain.com/blog/open-deep-research)).

The most important fact for a local build is that open models do not search enough on their own. BrowseComp-Plus measured Qwen3-32B at **3.49% accuracy with BM25 retrieval and 10.36% with Qwen3-Embedding-8B, against GPT-5's 55.90% and 70.12%**. The open model made fewer than 2 search calls despite prompting ([BrowseComp-Plus](https://arxiv.org/html/2508.06600v1)). Anthropic found that token spend explains **80% of BrowseComp performance variance** ([Anthropic engineering](https://www.anthropic.com/engineering/multi-agent-research-system)). Taken together, this means "let the model decide when it has searched enough" fails on local hardware. Code should set the breadth (how many sub-questions the planner must produce) and a minimum depth (at least K searches per sub-question, each followed by a gap check). The model's own sense that it is done should be a signal to stop early, not the only one.

The model's interface should be JSON decisions, not Ollama's `tools` field. Ollama 0.17.5 renders Qwen3 tool definitions as Go struct strings instead of JSON, a bug that needs a source change to fix ([ollama#14601](https://github.com/ollama/ollama/issues/14601)). Thinking combined with tools has produced empty output and unclosed `<think>` blocks that corrupt later turns ([ollama#10976](https://github.com/ollama/ollama/issues/10976)). gpt-oss tool calls have failed to parse during streaming and returned HTTP 500s ([ollama#11781](https://github.com/ollama/ollama/issues/11781); [ollama#17638](https://github.com/ollama/ollama/issues/17638)). Berkeley's format study found that small models are most accurate with JSON tool docs and JSON output, and lose the most with XML or custom tags. Some tool-specialised models drop "even to 0" when asked for an unfamiliar format ([BFCL V4](https://gorilla.cs.berkeley.edu/blogs/17_bfcl_v4_prompt_variation.html)). So each step should be a narrow call constrained by Ollama's `format` JSON schema. Ollama's docs also recommend repeating the schema in the prompt and using temperature 0 ([Ollama structured outputs](https://docs.ollama.com/capabilities/structured-outputs)). Validate each reply with Zod and retry up to a cap (open_deep_research uses 3) ([configuration.py](https://raw.githubusercontent.com/langchain-ai/open_deep_research/main/src/open_deep_research/configuration.py)). Read only `message.content`, never `thinking`. One untested gap remains: the docs do not say whether the `format` constraint still holds when `think` is on, so test that locally before relying on it.

One result points the other way. HuggingFace's smolagents scored **55.15% on GAIA with Python "code actions" versus 33% with JSON actions** ([HF blog](https://huggingface.co/blog/open-deep-research)). That test used frontier models, and a Bun server should not run Python the model wrote. The finding does not carry over here, but it does show that a too-rigid action format costs something. Keep the action menu small and expressive (search, read, answer) rather than splitting it into many micro-schemas.

| Candidate model | Fits in | Search-agent evidence (vendor-reported) | Caveat |
|---|---|---|---|

| MiroThinker v1.5-30B | 32 GB+ at 4-bit | BrowseComp 69.8, GAIA 80.8 ([card](https://huggingface.co/miromind-ai/MiroThinker-v1.5-30B)) | Trained on its own tool format; per-size figures inconsistent between sources |

For a prompted loop, a general model (Qwen3.5) is the lower-risk choice. The specialist models MiroThinker and Tongyi were trained on their own tool schemas, so they probably lose much of their edge when driven through generic JSON steps. If you try one, copy its repository's prompt format exactly.

## Keep every model call small: a rolling report, not a growing transcript

Ollama defaults to a **4096-token context and silently truncates** anything beyond it, so the server must send `options.num_ctx` on every request ([Ollama FAQ](https://docs.ollama.com/faq)). A bigger window is not the answer either. Chroma tested 18 models and found that all of them degrade as input grows, "even on simple tasks". Focused prompts of about 300 tokens beat full prompts of about 113K tokens on LongMemEval by a wide margin ([Chroma](https://www.trychroma.com/research/context-rot)). The leading open research agents converge on the same fix. Tongyi's working context holds only the question, "an evolving report S_t serving as compressed memory", and the last interaction ([Tongyi report](https://arxiv.org/html/2510.24701v1)). MiroThinker keeps only the **5 most recent tool results** ([MiroThinker](https://github.com/MiroMindAI/MiroThinker)), and Qwen's own agents prune older tool responses once they pass a size threshold ([Qwen3.5 card](https://huggingface.co/Qwen/Qwen3.5-35B-A3B)). These techniques also pay off without retraining. Used purely as a prompting strategy, IterResearch gained **up to 19.2 points over ReAct** on long tasks ([IterResearch](https://arxiv.org/abs/2511.07327)). ReSum's periodic summarization gained 4.5% without training ([ReSum](https://arxiv.org/abs/2509.13313)).

The concrete pipeline has five steps. Fetch the page. Extract the main content. Keep only the passages relevant to the current sub-question. Have the model write a short note that carries a verbatim quote and the source ID. Append that note to a capped notes buffer and drop the raw page. The planner then only ever sees the brief, the plan, the rolling notes and the latest result. Budgets of roughly 2–4K tokens per page excerpt are an inference, not a measurement, but they follow from the distractor findings. A 16K–32K `num_ctx` is enough for this design.

On a Mac, the bottleneck is prefill (reading the prompt), not generation. An M4 Max processes about **886 tokens per second of prompt but generates 83 tokens per second** on a 7B 4-bit model, and an M1 Pro manages 266 and 36 ([llama.cpp #4167](https://github.com/ggml-org/llama.cpp/discussions/4167)). Short prompts therefore matter twice: they help accuracy and they cut time. Three settings help further. Keep the system prompt byte-stable at the front of every call so the prefix cache can be reused. Never change `num_ctx` between calls. Pin the model for the whole run with `keep_alive` ([Ollama FAQ](https://docs.ollama.com/faq)). There is a real trade-off here. A rolling summary placed at the top of the prompt invalidates the cache every time it changes, so put the stable instructions first and the changing notes last.

Use one model for every role. Tongyi and MiroThinker both run planning, reading and synthesis inside a single model ([Tongyi report](https://arxiv.org/html/2510.24701v1)). Swapping models on a Mac means reloading 12–60 GB of weights, which costs seconds per swap (an estimate; no measurement was found). Vary the role through the system prompt, the `format` schema, `num_predict` caps and the thinking setting instead. Thinking strongly affects quality: gpt-oss-20b's AIME score moves from **42.1 to 80.0 to 92.1 across its low, medium and high reasoning levels** ([gpt-oss card](https://arxiv.org/html/2508.10925v1)). Spend it on planning and the final write-up, and turn it off (or to low on gpt-oss, which cannot fully disable it) for per-page extraction ([Ollama thinking](https://docs.ollama.com/capabilities/thinking)). Start the server with `OLLAMA_FLASH_ATTENTION=1` and `OLLAMA_KV_CACHE_TYPE=q8_0`, which halves the memory used by the context cache with minimal quality loss ([Ollama FAQ](https://docs.ollama.com/faq)). As a rough estimate, a 15-step run with about 6K new prompt tokens and 800 generated tokens per step takes **about 5 minutes on an M4 Max** with a model that has about 3B parameters active per token, and 2–4 times longer on M1/M2 Pro machines. That is an inference; no local wall-clock measurements were found.

## Retrieval quality is the cheapest lever: better results mean fewer, better searches

BrowseComp-Plus found that a better retriever both **raises accuracy and cuts 1–3 search calls** per question ([BrowseComp-Plus](https://arxiv.org/html/2508.06600v1)). For a local build, the retrieval layer may therefore be worth more than extra loops. Query writing comes first. Jina calls query rewriting "perhaps one of the most critical elements" and judges small models "probably unsuitable" for query expansion ([Jina guide](https://jina.ai/news/a-practical-guide-to-implementing-deepsearch-deepresearch/)). Have the main model break the question into sub-questions and write short keyword queries for each one. A practitioner comparison (a blog, not peer reviewed) found decomposition best for multi-hop questions, with recall@10 of **0.63 against 0.45 for HyDE**, and HyDE best for single-fact lookups ([dev.to](https://dev.to/gabrielanhaia/hyde-multi-query-decomposition-which-query-rewrite-actually-moves-recall-1m08)). HyDE means generating a hypothetical answer and searching with it. Search engines take keywords, so HyDE belongs at the local reranking stage, not in the query sent to ddgs. Merge results from several queries with Reciprocal Rank Fusion ([rag-fusion](https://github.com/Raudaschl/rag-fusion)), and skip any query that, after normalising, repeats one already run.

The search backends are fragile by nature. ddgs is now a metasearch library over Bing, Brave, DuckDuckGo, Google, Mojeek and others ([ddgs](https://github.com/deedy5/ddgs)), and its "202 Ratelimit" soft block shows up across Open WebUI, crewAI and other projects ([open-webui #6624](https://github.com/open-webui/open-webui/discussions/6624)). A deep run sends many more searches than a chat turn, so it will hit these limits. Copy SearXNG's design and treat each backend as a circuit breaker. SearXNG suspends an engine for **3600 s after a too-many-requests error and 86400 s after a CAPTCHA** ([SearXNG settings](https://docs.searxng.org/admin/settings/settings_search.html)). Cache results by normalised query and pages by canonical URL. Prefer free vertical sources where they fit: arXiv allows one request every 3 seconds ([arXiv ToU](https://info.arxiv.org/help/api/tou.html)). A self-hosted SearXNG would add a second scraper, but it hits the same upstream engines from the same home IP address, so it does not fail independently of ddgs.

For page extraction, Mozilla Readability.js scores **F1 0.947** on the ScrapingHub article benchmark against trafilatura's 0.958 ([article-extraction-benchmark](https://github.com/scrapinghub/article-extraction-benchmark)), and it runs in-process in Bun. Defuddle is a forgiving MIT-licensed alternative that also returns author, date and site metadata ([defuddle](https://github.com/kepano/defuddle)). A sensible cascade is plain fetch, then Readability, then a headless-browser re-fetch for pages that look JavaScript-rendered or come back nearly empty. ReaderLM-v2 is an option only for the hardest pages, and it carries a non-commercial license ([ReaderLM-v2](https://huggingface.co/jinaai/ReaderLM-v2)). PDFs need their own path. For filtering, BM25 in TypeScript over just the pages fetched in this run costs almost nothing. A small reranker such as bge-reranker-v2-m3 or jina-reranker-v3 (about 0.6B parameters, BEIR nDCG@10 of 56.51 and 61.94) ([jina-reranker-v3](https://arxiv.org/html/2509.25085v1)) would need a sidecar process, because Ollama has no rerank endpoint, and a second resident model competes for memory. Published numbers disagree on whether Qwen3-Reranker-0.6B beats bge ([Qwen3-Embedding #82](https://github.com/QwenLM/Qwen3-Embedding/issues/82)), so start with BM25 and add a reranker only if your own evaluation shows a gain. Remove near-duplicate pages in layers: canonical URL, then an exact hash of the content, then a 64-bit simhash within **3 bits**, the setting Google used for 8 billion pages ([Manku et al.](https://research.google.com/pubs/archive/33026.pdf)).

Security matters more in a deep run because the model reads dozens of untrusted pages. The existing SSRF guard must re-check every redirect hop and pin the resolved IP address to block DNS rebinding ([OWASP SSRF](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)). The headless-browser fallback needs the same guard, applied through request interception. Delimiting page text reduces prompt injection but does not stop it. Only architectural separation gives strong guarantees, where untrusted text cannot change control flow ([Willison on CaMeL](https://simonwillison.net/2025/Apr/11/camel/)). The code-owned loop already gives most of that separation. Page text can influence only notes and the choice among URLs that the system itself parsed from search results. It never sees private chat history, and it can never trigger any tool other than search or read.

## Citations by construction and a deadline that always reserves time to write

Citation honesty cannot be left to prompting. Across 10 models, **3–13% of citation URLs from deep-research agents had never existed**. Strong models fixed nearly all of them when given URL-checking feedback (GPT-5.1 went from 16.0% to 0.6%), but "smaller models failed to act on verification feedback despite tool access" ([arXiv 2604.03173](https://arxiv.org/html/2604.03173v1)). The largest single failure in the DEFT taxonomy is **"Strategic Content Fabrication" at 18.95%**, followed by too little retrieval at 16.30% ([DEFT](https://arxiv.org/html/2512.01948v1)). The fix is structural. The server gives each fetched source a numeric ID and passes notes as `[n] title — notes`. The writer may cite only `[n]`. The server removes any ID that is not in the registry and renders the reference list itself, so the model never types a URL. Quotes in notes are checked by substring match against the stored text. An optional entailment check ("does passage X support sentence Y?") can run per cited sentence if time allows. Write the final report in one call over the compressed notes, as open_deep_research does ([LangChain blog](https://www.langchain.com/blog/open-deep-research)).

Stopping rules should combine hard caps with a model check and a forced write-up. Jina's loop runs `while (tokenUsage < tokenBudget && badAttempts <= maxBadAttempts)`. When it runs out, "beast mode" forces a decisive answer from what it has gathered. Its answer evaluation runs as a separate call, because "answer generation and evaluation should not be in the same prompt" ([Jina guide](https://jina.ai/news/a-practical-guide-to-implementing-deepsearch-deepresearch/)). For this server, set one overall `max_seconds`. Check the deadline before every search, read and model call. Give each search and fetch its own timeout, and pass one AbortSignal through ddgs, fetch and the Ollama request. Hold back roughly 20–25% of the budget for the write-up. That share is a design choice; no source measured it. Stop early when a round adds no new URLs or domains. A failed search counts as one used step and emits the existing "unavailable" step event. If every backend fails, the tool returns `status: failed` with a sentence the chat model can pass on. This extends the M13 rule, so a deep run, like a plain web reply, can never hang.

The tool interface follows the existing examples. gptr-mcp ships `quick_search` and `deep_research` side by side, so the calling model can choose by need ([gptr-mcp](https://github.com/assafelovic/gptr-mcp)). Other servers expose only a query plus depth and breadth settings from 1 to 5 ([deep-research-mcp-server](https://www.mcpserverfinder.com/servers/ssdeanx/deep-research-mcp-server)). Anthropic writes its effort-scaling rules into the prompt: simple fact-finding gets **3–10 tool calls**, comparisons get 10–15 per subagent, and an early failure mode was over-spending effort on simple queries ([Anthropic engineering](https://www.anthropic.com/engineering/multi-agent-research-system)). Misunderstood requirements cause **10.55%** of DEFT failures ([DEFT](https://arxiv.org/html/2512.01948v1)), which supports turning the question into a short written brief before the expensive run, as open_deep_research and OpenAI both do ([OpenAI guide](https://developers.openai.com/api/docs/guides/deep-research)).

| Piece | Recommendation |
|---|---|
| Tool input | `question` (required); `depth`: `quick` \| `standard` \| `deep`. The server, not the model, sets `max_seconds` and the page caps |
| Tool output | `report` (markdown with `[n]`), `sources[]` (id, url, title, quote used), `status` (`complete` \| `partial` \| `failed`), `stats` (searches, pages, elapsed) |
| Tool description | Use `web_search` for single facts and current values; use `deep_research` for compare, survey, history and "all options" questions, or when more than 3 sources are clearly needed |
| Phases → events | brief → plan → search(query) → source(url) → read(url) → note → write, mapped onto the existing step and source events |
| Presets (to tune) | quick ≈ 3 sub-questions × 1 round (~2 min); standard ≈ 4 × 2 (~5 min); deep ≈ 6 × 3 (~10–15 min); at most 3 pages per round and 2 per domain; page text truncated to 8–12K characters |
| Concurrency | The run holds the only model; the server rejects or queues other replies, and the app shows elapsed time against the budget |

The presets and their times are starting points worked out from the throughput figures, not published values. For comparison, Perplexica's quick-to-thorough modes reportedly take 3–5 s, 8–15 s and 20–40 s ([Perplexica guide](https://joshuaopolko.com/perplexica-self-hosted-guide/)), while Open WebUI's "Deep Research at Home" is designed for 30–60 minute runs ([Open WebUI](https://openwebui.com/f/radeon/deep_research_at_home)).

## A replayable 20-question set catches regressions before the benchmarks would

Anthropic's advice is to start with **about 20 queries from real usage**, because early changes have large effects, scored by one LLM judge against a rubric covering factual accuracy, citation accuracy, completeness, source quality and tool efficiency ([Anthropic engineering](https://www.anthropic.com/engineering/multi-agent-research-system)). Locally, that becomes 20–40 real questions from the app, each with a short checklist of facts the answer must contain (in the style of FINDER) ([DEFT/FINDER](https://arxiv.org/html/2512.01948v1)). Record the search results and page bodies once into a fixture cache so runs replay offline and give the same result every time. That is the fixed-corpus idea behind BrowseComp-Plus and DeepResearchGym ([DeepResearchGym](https://arxiv.org/html/2505.19253)), and it fits the existing M13 fake-backend tests. Several metrics need no LLM at all: checklist recall, whether every `[n]` maps to a fetched source, the number of distinct domains, searches and pages used, elapsed time, and how often each `status` occurs. Fault-injection cases (all backends down, a slow backend, a deadline that hits during the write-up) must each still end with a reply. For an outside sanity check, BrowseComp-Plus ships about **100K documents, 830 questions and pre-built BM25 indexes**, and supports open models and a Qwen3-32B judge ([BrowseComp-Plus repo](https://github.com/texttron/BrowseComp-Plus)). A 50–100 question subset is practical. Expect low absolute scores. When using a local model as judge, prefer yes/no checklist judgments over 1–10 scales. No study was found on how well a local judge agrees with humans on research reports.

## Conclusion

Most published deep-research techniques were tuned on frontier models that already search eagerly and follow tool formats reliably. On local hardware the problem flips. The model has to be made to search enough, kept from reading too much at once, and stopped from inventing sources, and code solves all three better than prompts do. The newest trained agents (Tongyi, MiroThinker) and Qwen3.5 point the same way: a mixture-of-experts model with about 3B parameters active per token, running a bounded loop around an evolving report, is both the fastest shape on Apple Silicon and the shape that published context-management results favour. The biggest unknowns are local ones. Nobody has measured how 4-bit quantization changes agentic accuracy, how well small models judge whether they have found enough, or how long a full run takes on a given Mac. The replayable evaluation set is therefore not an extra. It is the only way to set the presets, choose between Qwen3.5 and a specialist model, and decide whether a reranker earns its memory.

The design also fits this codebase's existing commitments. The never-hang rule, the step and source events, and the SSRF guard each map directly onto a deadline-checked sub-loop that returns a typed result. The main new risk is the one with the strongest evidence behind it: running out of search capacity because of rate limits. Circuit breakers and caching therefore belong in the first version, not a later one.
